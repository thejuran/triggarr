## Summary

This is the round-3 re-review of WR-05 (`261026-s2v-REVIEW-2.md`): "WR-02's `stdin`
`error` handler has zero test coverage, and its fail-open interaction with the `end`
handler's `process.exit(0)` branches is untested." The fix commit (`b4e4a31`) adds a
module-level `refused` flag, set in the `error` handler, checked as an early return
at the top of the `end` handler; plus a new deterministic test that drives the
guard's own `process.stdin` via an `--import` preload that emits `data`, `error`,
then `end` directly (`EventEmitter.emit`), bypassing the OS pipe entirely for the
part that matters.

**WR-05 is confirmed resolved**, verified three independent ways rather than by
reading the diff alone:

1. Ran the full suite: 11/11 pass (`node --test .claude/plugins/planchk-router/test/planchk-router.test.mjs`).
2. Extracted `guard.mjs` at the pre-fix commit (`3c52116`) into a scratch copy and
   pointed the new test at it: it fails exactly as the fix record claims —
   `AssertionError: 0 !== 2` (actual `0`, expected `2`) — because the pre-fix `end`
   handler has no `refused` check and falls through to `process.exit(0)` on the
   non-matching payload emitted before the synthetic error. Pointed at the fixed
   `guard.mjs`, the same test passes.
3. Re-derived the fail-closed matrix from `261026-s2v-REVIEW-2.md` (non-matching
   payload + error, checker payload + error, checker payload + error + flag=1) and
   confirmed the sticky `refused` flag closes exactly the gap WR-05 names, with no
   new fail-open branch introduced: `data`'s handler is unconditional and harmless
   post-refusal (appends to an unused buffer), and re-firing `error` or `end` after
   `refused` is already `true` is idempotent (duplicate stderr write at worst, never
   a code-2-to-0 downgrade).

Two new issues were found by going beyond the diff and stress-testing the exact
scenario the task asked about — whether the `refused` early-return could leave the
process hanging with a real, OS-backed stdin left open. It does hang, but **not**
because of the `refused` flag: the identical hang reproduces against the pre-WR-05
code too (see WR-06 below), so this is a pre-existing gap surfaced by this round's
testing, not a regression introduced by `b4e4a31`. A second, directly-introduced
issue (WR-07) is that the new test itself has no timeout and would hang indefinitely
if that underlying defect, or any future wording change to the refusal message,
ever manifests.

No fail-open path was found anywhere in `guard.mjs` as it stands after this fix.

## Warnings

### WR-06: `guard.mjs`'s `error` handler never forces process exit, and a real (OS-backed) stdin left open after a stream error hangs the process indefinitely — pre-existing, not introduced by WR-05, but newly demonstrated

**File:** `.claude/plugins/planchk-router/hooks/guard.mjs:13-22`
**Issue:** The `error` handler only writes to stderr and sets `process.exitCode =
2`; it never calls `process.exit()`, destroys the stream, or otherwise releases the
handle. That is correct and deliberate for the case this round's test covers (a
stream error immediately followed by a real stream close/EOF, which is how Node
normally behaves) — once the real `end`/`close` happens, nothing is left on the
event loop and Node exits naturally with the exitCode already set.

But if the underlying stdin pipe's write side is never closed after the error (the
caller/host keeps the pipe open rather than closing it), there is nothing in this
handler that terminates the process. I reproduced this directly, independent of
`node:test`, with a `spawn`-based child whose stdin pipe the parent deliberately
never closes:

```
[child stderr] planchk-router: stdin error while reading PreToolUse input; refusing Agent spawn so the Codex route cannot silently fail. Stop and report.
STILL RUNNING after 4s with real stdin pipe left open by parent -- HANG CONFIRMED
```

I confirmed this is **not** caused by the `refused` flag added in this commit — the
identical hang reproduces against `guard.mjs` as it stood at `3c52116` (before
WR-05), using the same harness with only the synthetic `error` (no `end`) fired:
both the pre-fix and post-fix `guard.mjs` hang under this condition. So `refused`'s
early return is not the cause and is not a regression; this is a latent gap in the
`error` handler itself that WR-02 introduced and WR-05 did not touch.

Practically, the trigger condition is narrow (a genuine stream-level error on the
hook's stdin, where the host does not then close its write end), but the guard's
whole purpose is to be a fast, visible fail-closed backstop for a security-relevant
routing decision; a version of "fail closed" that can instead hang the PreToolUse
hook indefinitely trades a clear, visible block for a silent stall of the calling
session — worse for the owner's stated "failures must be visible" requirement than
the exit-2 path this handler otherwise achieves. The new test for this exact
handler (added in this same commit) only works at all because the test harness
knows to call `child.stdin.end()` itself, from the parent side, after seeing the
refusal message — i.e., the test's own author had to work around exactly this gap
to get a clean exit in the test, without flagging it as a product defect in
`guard.mjs`.
**Fix:** After writing the refusal message and setting `process.exitCode`, release
the handle explicitly so the process can exit regardless of what the caller does
with its end of the pipe, e.g.:
```js
process.stdin.on('error', () => {
  process.stderr.write(
    'planchk-router: stdin error while reading PreToolUse input; refusing Agent spawn so the Codex route cannot silently fail. Stop and report.\n'
  );
  refused = true;
  process.exitCode = 2;
  process.stdin.destroy(); // release the handle; don't wait on a caller that may never close its end
});
```
(Verify after the change that `destroy()` here does not itself race the pending
stderr write — if it does, pause/unref the stream instead of destroying it, or defer
the destroy to the stderr write's callback.)

### WR-07: The new WR-05 regression test has no timeout and depends on the exact refusal wording to clean itself up — a future regression can hang the test suite instead of failing it

**File:** `.claude/plugins/planchk-router/test/planchk-router.test.mjs:161-176`
**Issue:** The new test awaits `child.on('close', ...)` with no bound: no
`{ timeout }` option on the `test()` call, no `AbortSignal`, and no `--test-timeout`
assumption documented anywhere (Node's test runner has no default per-test
timeout). The only thing that causes the child to actually exit is the parent
calling `child.stdin.end()`, which itself only happens if the accumulated
`child.stderr` text contains the literal substring `'stdin error'`
(`planchk-router.test.mjs:169`).

This creates a direct coupling to WR-06: if that handle-never-released defect
manifests in any real scenario this test doesn't already special-case, or if a
future edit changes the refusal wording (e.g. rewords "stdin error" out of the
message, or the write is skipped on some other branch), `child.stdin.end()` is never
called, the real OS pipe never closes, the child hangs exactly as demonstrated in
WR-06, and `await new Promise((resolve) => child.on('close', resolve))` never
resolves. Locally this hangs the developer's `node --test` invocation indefinitely
(confirmed by construction — this is the same mechanism as WR-06, just witnessed
through the test rather than through a hand-rolled harness). This test file is not
currently wired into `.github/workflows/ci.yml` (CI only runs
`.github/scripts/*.test.cjs`), so it would not hang CI today, but it would hang
anyone running the plugin's own test suite per its documented local workflow, with
no actionable failure message — just a stuck process.
**Fix:** Bound the wait explicitly and kill the child on timeout so a regression
produces a clear test failure instead of a hang:
```js
test('guard: stdin error then end -> stays exit 2, refusal on stderr (no later exit 0)', { timeout: 5000 }, async () => {
  const env = { ...process.env };
  delete env.CLAUDE_CODE_ENABLE_FUNCTION_HOOKS;
  const child = spawn(process.execPath, ['--import', STDIN_ERROR_PRELOAD, GUARD_PATH], { env, timeout: 5000 });
  let stderr = '';
  child.stderr.setEncoding('utf8');
  child.stderr.on('data', (chunk) => {
    stderr += chunk;
    if (stderr.includes('stdin error')) {
      child.stdin.end();
    }
  });
  const code = await new Promise((resolve) => child.on('close', resolve));
  assert.equal(code, 2);
  assert.match(stderr, /planchk-router: stdin error while reading PreToolUse input/);
});
```
(`child_process.spawn`'s own `timeout`/`killSignal` options, or `node:test`'s
per-test `timeout`, either one closes the gap; use both for a clear failure message
instead of a silent hang either in CI or on a laptop.)
