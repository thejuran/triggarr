## Summary

This is the round-4 re-review of WR-06 and WR-07 from `261026-s2v-REVIEW-3.md`.
WR-06: `guard.mjs`'s stdin `error` handler could leave the process hanging forever
if the caller never closes stdin after a stream error. WR-07: the regression test
for that handler had no timeout and would hang the test runner under the same
condition. The fix commit (`a805f3f`) changes the `error` handler to call
`process.exit(2)` from inside the `process.stderr.write()` completion callback
(instead of only setting `process.exitCode = 2` and waiting for a natural exit that
never comes if stdin stays open), and updates the test to add a `{ timeout: 5000 }`
test-level bound, a 3s `setTimeout(() => child.kill('SIGKILL'), 3000)` watchdog, a
`child.stdin.on('error', () => {})` guard, and an unconditional `child.stdin.destroy()`
during cleanup — removing the old `child.stdin.end()`-on-message-match coupling that
made the test's own exit depend on exact refusal wording.

**Both WR-06 and WR-07 are confirmed resolved**, verified independently of reading
the diff:

1. Ran the suite three times: 11/11 pass each run (`node --test
   .claude/plugins/planchk-router/test/planchk-router.test.mjs`), the stdin-error
   test completing in ~65-72ms each time — it resolves via the guard's own
   `process.exit(2)`, never via the 3s/5000ms backstops.
2. Extracted `guard.mjs` at the pre-fix commit (`b4e4a31`) into a scratch copy and
   drove it with the exact preload+harness pattern the test uses, but without the
   test's own 3s kill-watchdog removed (i.e. reproducing WR-06 directly): it hangs
   past 3s and had to be `SIGKILL`ed, closing with `code=null, signal=SIGKILL`
   after ~3001ms. Pointed at the fixed `guard.mjs`, the identical harness closes
   with `code=2, signal=null` in ~66ms, with the full refusal message present on
   stderr both times (`stderr: "planchk-router: stdin error ... Stop and report.\n"`)
   — confirms the fix resolves the hang without losing the message.
3. Re-ran the current test file's exact watchdog logic (test-level `{ timeout: 5000
   }` plus the in-test `setTimeout(..., 3000)` kill) and confirmed it is *not*
   load-bearing for the passing case (the guard exits in ~70ms on its own) but does
   correctly convert a hang into a clean `AssertionError: null !== 2` instead of an
   indefinite hang when pointed at the old, pre-fix guard — exactly the regression
   WR-07 was raised against.
4. Checked every `process.exit(0)` site in `guard.mjs` (lines 46, 51): both are
   inside the `end` handler and both are still gated by the `if (refused) return;`
   early return, which is set synchronously inside the `error` handler before the
   async `process.exit(2)` from the write callback ever runs. Because `refused` is
   set synchronously, there is no ordering in which a subsequent `end` emission can
   downgrade the exit code to 0 after an `error`, even though the new test's title
   no longer spells that guarantee out explicitly (cosmetic only — the underlying
   assertion (`code === 2`) still proves it, since `process.exit(0)` would pre-empt
   the pending `process.exit(2)` if it were ever reached).

No fail-open path was found anywhere in `guard.mjs`'s current `error` handler, and
no scenario was found in which it exits 0 or drops the refusal message. All spawned
child processes from this verification were confirmed closed (`ps aux` shows no
leftover `guard.mjs`/`guard-old.mjs` processes after the session).

## Info

### IN-01: `error` handler's `process.stderr.write` completion callback silently discards a write error

**File:** `.claude/plugins/planchk-router/hooks/guard.mjs:21-24`
**Issue:** `process.stderr.write(msg, () => process.exit(2))` ignores the callback's
`error` argument. In the overwhelming majority of cases this is harmless — the exit
code contract (fail closed, exit 2) is preserved either way since `process.exitCode
= 2` is already set beforehand and `process.exit(2)` runs unconditionally from the
callback. But if the write itself fails (e.g. stderr already closed/EPIPE in some
exotic host), the refusal message can be lost silently with no record of why, which
is a thin edge case but still a "don't swallow errors silently" style gap for an
otherwise carefully-commented fail-closed path.
**Fix:** Log the write error to the exit path for diagnosability without changing
the exit contract:
```js
process.stderr.write(
  'planchk-router: stdin error while reading PreToolUse input; refusing Agent spawn so the Codex route cannot silently fail. Stop and report.\n',
  (err) => {
    if (err) {
      try { process.stderr.fd && require('node:fs').writeSync(2, `planchk-router: refusal message write failed: ${err.message}\n`); } catch {}
    }
    process.exit(2);
  }
);
```
(Or more simply: accept the current behavior as-is — the exit code is unaffected
either way — and only act on this if the project wants write-failure visibility on
this specific backstop path. Not blocking.)
