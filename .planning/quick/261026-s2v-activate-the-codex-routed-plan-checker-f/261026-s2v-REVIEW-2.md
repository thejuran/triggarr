## Warnings

### WR-05 (new): WR-02's `stdin` `error` handler has zero test coverage, and the fix record's "impractical to test" conclusion is avoidable

**File:** `.claude/plugins/planchk-router/hooks/guard.mjs:11-19`
**Issue:** The fix record (`261026-s2v-REVIEW-FIX.md`, WR-02 section) documents two
failed attempts to synthesize a genuine OS-level `stdin` stream error from the test
harness, concludes a reliable test "would require relying on non-deterministic,
platform-dependent kernel/timing behavior," and ships the handler with no test —
only "code review of the one-line change."

That conclusion is avoidable: both failed attempts tried to force a *real* OS-level
error onto the *child's* stdin from the *parent* side of a pipe. A simpler,
fully deterministic technique works instead — import `guard.mjs` inside the *same*
process as the test (registering its listeners on that process's own `process.stdin`),
then call `process.stdin.emit('error', new Error(...))` directly. `EventEmitter`
listeners run identically whether the event is organic or emitted programmatically,
so this exercises the exact registered handler with no flakiness and no kernel
dependency. I verified this works:

```
$ node /tmp/error_harness.mjs "file://.../guard.mjs" < /dev/null
planchk-router: stdin error while reading PreToolUse input; refusing Agent spawn so the Codex route cannot silently fail. Stop and report.
exit=2
```

Using this technique I also checked the exact regression the original WR-02 worried
about — a stream error overlapping with the `end` handler's pass-through branches,
which call `process.exit(0)` (an explicit argument to `process.exit()` overrides
any previously-set `process.exitCode`, per Node's own `process.exit()` semantics).
I drove all three cases:

| stdin payload | flag | synthetic `error` fired | observed exit |
|---|---|---|---|
| non-matching subagent, valid JSON | unset | yes | `0` (error's `exitCode=2` overridden — but this branch is a legitimate pass-through regardless of the error; not a guard-scope violation) |
| `bm:bm-plan-checker`, valid JSON | unset | yes | `2` (no override — this branch only ever sets `exitCode = 2`, never calls `process.exit()`, so it cannot override anything) |
| `bm:bm-plan-checker`, valid JSON | `"1"` | yes | `0` (legitimate — the module hook is active, nothing to block) |

The one case that matters — `bm:bm-plan-checker` with the flag not `"1"` — stays
fail-closed even under this synthetic double-fire, so there is no currently
observable fail-open bug. But that correctness is an accident of today's branch
ordering (the two `process.exit(0)` calls happen to sit only in branches that are
correct independent of stream state), not something the code defends explicitly. A
future edit that adds a new early-return `process.exit(0)` branch to the `end`
handler — for any reason, in any position — would silently reopen exactly the
fail-open gap WR-02 exists to prevent, and nothing in the test suite would catch it,
because the `error` handler has no test at all.
**Fix:** Add a same-process emit-based test (no subprocess needed for this one case,
since we want to invoke the listener directly), and consider an explicit "already
decided" guard so correctness is structural rather than incidental:
```js
// test/planchk-router.test.mjs
test('guard: synthetic stdin error -> exit 2 via EventEmitter.emit (no OS dependency)', async () => {
  const r = spawnSync(process.execPath, ['--input-type=module', '-e', `
    await import(${JSON.stringify(pathToFileURL(GUARD_PATH).href)});
    process.stdin.emit('error', new Error('synthetic'));
  `], { input: '', encoding: 'utf8' });
  assert.equal(r.status, 2);
  assert.match(r.stderr, /stdin error while reading PreToolUse input/);
});
```
```js
// guard.mjs — make the invariant structural, not incidental
let erroredClosed = false;
process.stdin.on('error', () => {
  erroredClosed = true;
  process.stderr.write('...');
  process.exitCode = 2;
});
process.stdin.on('end', () => {
  if (erroredClosed) return; // already decided; never let a later branch override
  ...
});
```
