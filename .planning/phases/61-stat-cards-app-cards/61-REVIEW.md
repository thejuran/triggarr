## Warnings

### WR-01: Unguarded arithmetic on potentially-None stat counts in stats_row.html

**File:** `triggarr/templates/partials/stats_row.html:44`

**Issue:** The Movies, Series, and Albums stat cards evaluate `stats.movies_found + stats.movies_updated`, `stats.episodes_found + stats.episodes_updated`, and `stats.albums_found + stats.albums_updated` without checking whether the operands are `None`. The Grab Rate card correctly guards with `{% if stats.overall_rate is not none %}` before rendering, but the count additions do not. If the route populates these fields as `None` (e.g. when the respective app is disabled or has never run), Jinja2 will raise a `TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'` and return a 500 response.

**Fix:** Wrap each count addition the same way the missing/cutoff counts are guarded in `app_card.html`, using either a `default(0)` filter or an explicit `is not none` check:

```html
<!-- Movies card -->
<div class="text-[32px] font-bold text-triggarr-text leading-none mb-3">
  {% if stats.movies_found is not none and stats.movies_updated is not none %}
    {{ stats.movies_found + stats.movies_updated }}
  {% else %}&mdash;{% endif %}
</div>
```

Apply the same pattern to `episodes_found + episodes_updated` (line 58) and `albums_found + albums_updated` (line 72).

### WR-02: Waiting-state connection pill missing border — inconsistency between template and test assertion

**File:** `triggarr/templates/partials/app_card.html:22`

**Issue:** The Connected pill (line 18) renders `border border-triggarr-primary/20` and the Unreachable pill (line 20) renders `border border-triggarr-danger/20`, but the Waiting/`None` pill (line 22) renders `border border-triggarr-border/40` — using the same opacity value as the background (`bg-triggarr-border/40`). `test_waiting_pill_unified_shape` (test_app_cards.py:151) only asserts the pill shape classes and muted colours, so the border does not fail the test. However if the design spec intended a visually-distinct border (as implied by the Connected and Unreachable pill design), `border-triggarr-border/40` against `bg-triggarr-border/40` renders as invisible. This is either a spec gap or a copy-paste error.

**Fix:** If the Waiting pill is meant to have a visible border, change its opacity to a different value:

```html
<span class="px-2 py-0.5 rounded text-[10px] font-bold uppercase tracking-wider
             bg-triggarr-border/40 text-triggarr-muted border border-triggarr-border/20">Waiting...</span>
```

If no visible border is intended, remove the `border` classes entirely to avoid ambiguity.

### WR-03: test_output_css_contains_mini_bar reads generated file — will fail in clean CI

**File:** `tests/test_stats_health.py:224`

**Issue:** The test reads `STATIC_DIR / "css" / "output.css"` (the compiled Tailwind output) and asserts that `"mini-bar"` is present. This file is generated by the Tailwind CLI build step and is not committed to the repo (it is in `.gitignore` or equivalent). In a clean CI checkout where `uv run tailwindcss ...` has not been executed, `output.css` will either be absent (raising `FileNotFoundError`) or stale. The `test_css_has_card_hover_rule` and `test_css_has_danger_stripes_rule` tests in `test_app_cards.py` correctly target `input.css` (the source file).

**Fix:** Move the assertion to `input.css` where the `.mini-bar` rule is defined (line 70–71 of `input.css`), consistent with the other CSS rule tests:

```python
def test_css_has_mini_bar_rule():
    """input.css contains .mini-bar rule with height and border-radius."""
    css_path = STATIC_DIR / "css" / "input.css"
    css = css_path.read_text()
    assert ".mini-bar" in css
    assert "height: 6px" in css
```

If the intent is specifically to verify the compiled output (e.g. Tailwind JIT didn't purge the class), document this as a build-integration test and ensure CI runs the CSS build before the test suite. Add a clear `pytest.skip` or `pytest.importorskip` guard for when `output.css` does not exist.

### IN-02: Async fixture yields inside aiosqlite context — connection closed before tests run

**File:** `tests/test_app_cards.py:35` and `tests/test_stats_health.py:41`

**Issue:** Both `test_app` fixtures use `async with aiosqlite.connect(db_path) as db:` and then `yield app` inside that context manager. This is the intended pattern for keeping the DB alive during each test. However, `app.state.db = db` assigns the in-context connection to app state, and `TestClient` (a synchronous Starlette wrapper) may interact with the async DB connection across thread boundaries if any route handler awaits `app.state.db` outside the asyncio event loop that owns the connection. If route handlers use `request.app.state.db` directly, they will be using the connection from the fixture's event loop, which may differ from the TestClient's internal event loop. This is a latent reliability risk rather than a definite crash today, but it will surface as intermittent `aiosqlite` errors under `asyncio_mode=auto` with certain pytest-asyncio versions.

**Fix:** Confirm that routes consistently acquire DB connections through a dependency (e.g. `get_db` that opens a new connection per-request) rather than reading `app.state.db` directly, or document why the shared fixture connection is safe in the test context.
