<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated browser → /login | First-run and locked-out users render the login page before any session exists |
| unauthenticated browser → /reset/* | Recovery routes are deliberately reachable without a session (exempt via the /reset predicate); untrusted input crosses here |
| route handler → reset.html / login.html context | Server-rendered Jinja under the global CSP nonce; whatever lands in context is reflected to an unauthenticated client |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-73-01 | Information Disclosure | reset.html message/onward-link branch | mitigate | The request-confirmation branch renders ONLY `{{ message }}` (a fixed neutral string) — the plan forbids referencing any token-valued context variable in markup (Task 2 acceptance: grep shows no rendered token; message branch references only `message`). Inherits Phase 72 D-02: token never enters any response/header/context. test_token_not_in_response stays green (Task 3). |
| T-73-02 | Elevation of Privilege | new GET /reset/confirm route | mitigate | The route is reachable unauthenticated by design (inherits the /reset exemption) but the plan makes NO middleware change — `git diff middleware.py` must be empty (Task 1 + Task 3 acceptance). The exact-or-/reset/ predicate keeps /resetXYZ and all other routes gated; existing test_no_other_route_exposed proves the exemption did not widen. |
| T-73-03 | Information Disclosure | login.html "Forgot password?" link | mitigate | The link is wrapped in `{% if not needs_setup %}` so it is absent during first-run setup, never advertising a recovery surface before auth is configured. Enforced by test_forgot_password_link_absent_during_setup (Task 2). |
| T-73-04 | Tampering | confirm-page password/token error rendering | accept | Token failures stay in the page-level generic banner; password failures stay inline per-field — both rendered from the locked Phase 72 `error`/`errors` contracts with no backend change. Generic token error reveals nothing about why a token was rejected (no oracle). Phase 73 only verifies the existing rendering (D-03/D-03a); rationale: no new attack surface, server-side validation unchanged. |
| T-73-SC | Tampering | npm/pip/cargo installs | accept | No package installs in this phase — pure template + route + test edits against existing dependencies. No legitimacy audit required; nothing to mitigate. |

No high-severity (mitigate-required) threat is left unmitigated: T-73-01 (token leak) and T-73-02 (exemption widening) are the two adversarial-weight invariants from the security gate and both carry concrete, test-backed mitigations.
