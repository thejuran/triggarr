<objective>
Implement `reset_confirm_post` — the apply path — mirroring `change_password` (routes.py:1401) exactly, with the current-password verify replaced by in-lock token validation (possession of the token IS authorization — no identity check, per D-01), plus auto-login and token-file deletion. This handler is one of the three /reset routes that live in routes.py reusing the existing helper chain (D-23 component boundary). On a valid token + matching new password it rehashes, rotates `session_secret`, persists atomically with `0600`, reloads settings, refreshes the redacting sink, clears the in-memory token, deletes the token file, and 303-redirects to the dashboard with a fresh cookie signed by the NEW secret. All failure modes (bad/expired/used/superseded token, password problems, rate-limit) leave state untouched and surface generic/field errors.

Purpose: Deliver RCOV-04 (new hash + session rotation + auto-login), the validation/single-use half of RCOV-03 (TTL reject, single-use, supersession reject), the confirm half of RCOV-05 (5s rate-limit), and the token-file-delete half of RCOV-06.
Output: one handler in `triggarr/web/routes.py`; the remaining 11 confirm/rotation/error/rate-limit/delete tests in tests/test_reset.py go GREEN; full suite (984 + 20 reset) green.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated client → POST /reset/confirm | Token bearer (proves host access) submits a new password |
| in-memory token → persisted auth | Token validation gates a write to triggarr.toml (hash + session_secret) |
| old session cookies → rotated secret | All pre-reset cookies must stop validating |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-72-expiry | Spoofing | token TTL | mitigate | `time.monotonic() >= stored[1]` reject inside lock (D-06); test_expired_token_rejected. |
