<objective>
Implement the reset-request path: `reset_request_page` (GET form shell), `reset_request_post` (POST mint), and the private `_write_reset_token_file` helper. Minting generates a CSPRNG token, stores it in-memory with a 15-minute monotonic TTL, logs the token value exactly once at `warning` (the deliberate operator-only recovery channel per D-02 + RESEARCH #4), and writes a `0600` token file atomically. The token value lives in exactly two operator-only sinks — the warning log and the `0600` file — and NEVER appears in any HTTP response. Both the GET and POST land under the `/reset` exemption from Plan 01.

Purpose: Deliver RCOV-02 (mint + log + 0600 file, never in response), the mint half of RCOV-03 (in-memory store, 15-min TTL, supersession of expired tokens only), the request half of RCOV-05 (60s rate-limit), and the GET-reachability half of RCOV-06.
Output: three additions to `triggarr/web/routes.py`; the 9 request/mint/rate-limit/reachability/supersession tests in tests/test_reset.py go GREEN.
</objective>

    Add `import tempfile` to routes.py imports (alongside os/asyncio).

    Add private `_write_reset_token_file(path: Path, token: str) -> None` mirroring `_atomic_toml_write` (config.py:95-163) with one deliberate deviation for M1: open the mkstemp fd in text mode ("w"), set the final permission on the OPEN temp fd BEFORE the rename via `os.fchmod(fd, 0o600)` (or `os.chmod(tmp_path, 0o600)` on the temp path) so the renamed file is already 0600 and NO post-replace chmod is needed; then `f.write(token)` + `f.flush()` + `os.fsync(f.fileno())`, then `os.replace(tmp_path, path)`, then open+fsync the parent dir. There must be NO `os.chmod(path, ...)` AFTER `os.replace` — that post-rename chmod could raise FileNotFoundError on a path that was never created and defeat the non-fatal guarantee (M1). On OSError BEFORE rename: log at `error` with ONLY the path + exception (NEVER the token string — Pitfall 1), unlink the temp file, and DO NOT re-raise (D-17: in-memory token is the authority AND the token is already in the warning log, so the file write is non-fatal). On OSError after rename (dir fsync): log at `warning` (path + exception, no token), proceed. Ensure the error-before-rename path never reaches any chmod on the final path. This helper is synchronous and dispatched via run_in_executor.

    Add `@router.get("/reset/request", response_class=HTMLResponse) async def reset_request_page(request)` returning `templates.TemplateResponse(request=request, name="reset.html", context={"step": "request"})`. No auth (exempt prefix from Plan 01). Per PATTERNS.md, also accept GET "/reset" if convenient, but the canonical form path is /reset/request (the test hits /reset/request).

    Add `@router.post("/reset/request") async def reset_request_post(request)`: apply the search_now rate-limit pattern with `rate_key = "request"`, `app.state.last_reset_time`, and `RESET_REQUEST_RATE_LIMIT_SECONDS` — optimistic check before the lock (429 on throttle), then `async with request.app.state.search_lock:` re-check (429), set `last_reset_time["request"] = time.monotonic()`. Then apply the H1 live-token guard BEFORE minting: read `stored = request.app.state.reset_token`; if `stored is not None` AND `time.monotonic() < stored[1]` (a live, unexpired token already exists), DO NOT mint — leave `app.state.reset_token` untouched, do NOT reset the TTL, do NOT rewrite the file, and return the SAME neutral confirmation (the operator who just minted still holds their valid token). Only when no token exists OR the existing token is expired do you mint: `token = generate_reset_token()`, `request.app.state.reset_token = (token, time.monotonic() + 900)` (D-05; this assignment supersedes any expired/absent prior). Per D-02 + RESEARCH #4, log EXACTLY ONE warning line that INCLUDES the token value AND names the recovery channels (docker logs + reset-token.txt) — this is the deliberate operator-only recovery channel; the reset token is intentionally NOT added to collect_secrets / the redacting sink (unlike session_secret/password_hash). Then write the file: `token_path = _runtime_config_dir(request) / "reset-token.txt"`, dispatched as `await asyncio.get_running_loop().run_in_executor(None, _write_reset_token_file, token_path, token)`. Return a neutral `templates.TemplateResponse(request=request, name="reset.html", context={"step": "request", "message": <neutral copy>})` — the context MUST NOT contain the token (Pitfall 5: the token's two sinks are the warning log + the 0600 file, never any HTTP response). The neutral message tells the operator to read the token from docker logs or reset-token.txt in the config volume (final wording is Phase 73; the contract — neutral, no token in the response, points at log + file — is locked here).

    Lock scope: hold search_lock for the rate-check + timestamp update + the live-token guard + mint (RESEARCH.md Open Question 1 recommendation — consistent with search_now, prevents a concurrent double-mint race; the live-token guard must also be inside the lock so two concurrent requests cannot both decide to mint). The file write may run inside or just after releasing the lock; keep it via run_in_executor either way (it does not touch search_lock).

    D-05 refinement note (H1): supersession ("a new mint overwrites the prior token") now applies ONLY when the prior token is expired or absent. While a live token exists, a fresh /reset/request is a no-op returning the same neutral confirmation. This closes the unauthenticated-supersession DoS (a remote attacker hitting /reset/request every 60s can no longer perpetually invalidate a legitimate operator's in-progress token), keeping "remote attacker gains nothing" (D-03) intact while preserving the single-operator recovery flow, and stays entirely within the existing in-memory model (no new persistent state).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated client → POST /reset/request | Remote/locked-out caller triggers a token mint |
| process → config volume | Token written to a 0600 file in the config dir (operator-only sink #1) |
| process → application log | Token logged once at warning for operator retrieval (operator-only sink #2) |

> Milestone invariant (D-03): these endpoints add ZERO new network attack surface — a remote attacker who can hit them still cannot read the token via HTTP (it is never in any response; its only two sinks are the warning log and the 0600 config-volume file, both requiring host/filesystem access) and is throttled by the rate limits + live-token no-op below.
