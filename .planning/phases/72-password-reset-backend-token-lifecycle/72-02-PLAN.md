<objective>
Implement the reset-request path: `reset_request_page` (GET form shell), `reset_request_post` (POST mint), and the private `_write_reset_token_file` helper. Minting generates a CSPRNG token, stores it in-memory with a 15-minute monotonic TTL, logs it exactly once at `warning`, and writes a `0600` token file atomically — and the token value never leaves the process in any HTTP response. Both the GET and POST land under the `/reset` exemption from Plan 01.

Output: three additions to `triggarr/web/routes.py`; the 9 request/mint/rate-limit/reachability tests in tests/test_reset.py go GREEN.

    Add `import tempfile` to routes.py imports (alongside os/asyncio).

    Add private `_write_reset_token_file(path: Path, token: str) -> None` mirroring `_atomic_toml_write` (config.py:95-163) but: open the mkstemp fd in text mode ("w"), `f.write(token)` + `f.flush()` + `os.fsync(f.fileno())`, `os.replace(tmp_path, path)`, open+fsync the parent dir, then `os.chmod(path, 0o600)` AFTER the replace (Pitfall 6). On OSError before rename: log at `error` with ONLY the path + exception (NEVER the token string — Pitfall 1), unlink the temp file, and DO NOT re-raise (D-17: in-memory token is the authority, file write is non-fatal). On OSError after rename (dir fsync): log at `warning`, proceed. This helper is synchronous and dispatched via run_in_executor.

    Add `@router.get("/reset/request", response_class=HTMLResponse) async def reset_request_page(request)` returning `templates.TemplateResponse(request=request, name="reset.html", context={"step": "request"})`. No auth (exempt prefix from Plan 01). Per PATTERNS.md, also accept GET "/reset" if convenient, but the canonical form path is /reset/request (the test hits /reset/request).

    Add `@router.post("/reset/request") async def reset_request_post(request)`: apply the search_now rate-limit pattern with `rate_key = "request"`, `app.state.last_reset_time`, and `RESET_REQUEST_RATE_LIMIT_SECONDS` — optimistic check before the lock (429 on throttle), then `async with request.app.state.search_lock:` re-check (429), set `last_reset_time["request"] = time.monotonic()`, then mint: `token = generate_reset_token()`, `request.app.state.reset_token = (token, time.monotonic() + 900)` (D-05; a new mint overwrites the prior — supersession is implicit in the assignment). Log EXACTLY ONE warning line that names the recovery channels (docker logs + reset-token.txt) but does NOT include the token value (D-02). Then write the file: `token_path = _runtime_config_dir(request) / "reset-token.txt"`, dispatched as `await asyncio.get_running_loop().run_in_executor(None, _write_reset_token_file, token_path, token)`. Return a neutral `templates.TemplateResponse(request=request, name="reset.html", context={"step": "request", "message": <neutral copy>})` — the context MUST NOT contain the token (Pitfall 5). The neutral message tells the operator to read the token from docker logs or reset-token.txt in the config volume (final wording is Phase 73; the contract — neutral, no token, points at log + file — is locked here).

    Lock scope: hold search_lock for the rate-check + timestamp update + mint (RESEARCH.md Open Question 1 recommendation — consistent with search_now, prevents a concurrent double-mint race). The file write may run inside or just after releasing the lock; keep it via run_in_executor either way (it does not touch search_lock).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated client → POST /reset/request | Remote/locked-out caller triggers a token mint |
| process → config volume | Token written to a file in the config dir |
| process → application log | Token logged once at warning for operator retrieval |

> Milestone invariant (D-03): these endpoints add ZERO new network attack surface — a remote attacker who can hit them still cannot read the token (never in any response) and is throttled by the rate limits below.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-72-redaction | Information Disclosure | reset_request_post response + log/file-error paths | mitigate | Token never placed in response body/headers/context (test_token_not_in_response); the single warning log line and all OSError messages reference only channels/paths, never the token value (Pitfall 1; redaction grep in verification). |
| T-72-fileperm | Information Disclosure | reset-token.txt | mitigate | Atomic temp-then-rename + `os.chmod(path, 0o600)` after replace (test_token_file_written_0600). |
| T-72-flood | Denial of Service | POST /reset/request | mitigate | RESET_REQUEST_RATE_LIMIT_SECONDS=60 monotonic gate, optimistic + in-lock double-check (search_now pattern); test_request_rate_limited → 429. |
| T-72-overexpose | Elevation of Privilege | /reset GET reachability | mitigate | Exemption scoped to /reset prefix only (Plan 01); test_no_other_route_exposed confirms GET / still redirects to /login. |
| T-72-filefail | Availability/Integrity | _write_reset_token_file OSError | accept (degrade gracefully) | Per D-17 the file write is non-fatal; OSError is logged (sanitized) and the request still returns the neutral confirmation. In-memory token remains the authority. |
| T-72-SC | Tampering | npm/pip/cargo installs | accept | No packages installed (stdlib `tempfile`/`os`/`asyncio`/`secrets` only). |
