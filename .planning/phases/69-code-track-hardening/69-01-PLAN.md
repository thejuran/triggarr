<objective>
Close the two repo-hygiene / secret-scan-tooling fold-in findings from Phase 68 discovery:
P68-FI-004 (`.orchestrator.json` not git-ignored) and P68-FI-001 (`.gitleaksignore` non-functional
under gitleaks 8.30.x). Both are tooling/repo-metadata changes with zero application-behavior impact —
a skeptical r/selfhosted reviewer who runs `git status`, `git check-ignore`, or `gitleaks git .` must
see a clean, intentional secret-scan posture and no stray runtime-state file.

Purpose: Remove the two launch-visible "sloppy-tooling tells" so the repo reads as carefully maintained.
Output: An updated `.gitignore` (with `.orchestrator.json`) and a rewritten `.gitleaksignore`
(gitleaks-8.x fingerprints) that produces a clean scan (gitleaks exits 0 / `no leaks found`) with no "Invalid entry" warnings.

KNOWN BRITTLENESS (acknowledged, not fixed — D-07 is LOCKED): gitleaks git-history fingerprints are
per-commit (`commitSHA:filepath:rule:line`). The SAME false positive in a NEW commit produces a NEW
fingerprint, so the allowlist grows unboundedly with history and `gitleaks git .` only exits clean when
EVERY historical occurrence has its own line. This is an inherent cost of the `.gitleaksignore`
fingerprint mechanism (D-07 keeps the allowlist in `.gitleaksignore`, NOT a new `gitleaks.toml` with
path/rule allowlist rules). This plan accepts that cost; the executor mitigates it by regenerating the
FULL fingerprint set from a live run and verifying a clean scan (gitleaks exit 0) after writing — it does NOT
switch config files. Maintenance note: a future commit that touches any of these allowlisted paths will need a
fingerprint refresh (re-run gitleaks, re-write the set).
</objective>
