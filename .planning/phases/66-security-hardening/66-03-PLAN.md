<objective>
Add a sync helper `_warn_if_session_secret_short(settings: Settings) -> None`
to `triggarr/startup.py` that emits a single WARNING via loguru when the
persisted `auth.session_secret` is shorter than 32 characters AND
`auth.needs_setup` is False. The helper is modeled exactly on the existing
`check_localhost_urls` shape (sync function, takes `settings`, calls
`logger.warning(...)`). The helper is invoked once from `startup()` between
`print_banner()` and the `has_enabled_app` check / `check_localhost_urls`
call.

Purpose: SEC-04. Today, a user who hand-edits `triggarr.toml` and pastes a
short value into `auth.session_secret` (or accidentally truncates it) is
silently running with an under-strength HMAC key behind itsdangerous session
signing. The startup warning gives them a one-shot, actionable nudge with the
exact remediation path: "regenerate via Settings → Security or set a longer
value in config.toml". Per D-12, the warning fires once at startup — NOT
periodically (the misconfiguration is transient; once fixed by the user, the
next startup is silent).

Per D-13: the `needs_setup` guard prevents false positives during the
pre-setup state, where `session_secret == ""` is normal until the user
completes the setup flow (which always persists a freshly-generated 64-char
hex value atomically — verified at routes.py:1089-1112).

Per D-14 / RESEARCH Pattern 4: the helper follows the `check_localhost_urls`
template (`triggarr/startup.py:25-46`), NOT the `_warn_if_auth_disabled`
function (which does not exist — verified by RESEARCH Assumption A4). The
helper is sync, single-shot, and called from the linear `startup()` flow.

**SecretStr discipline (CLAUDE.md):** Calling `.get_secret_value()` to
measure length is allowed under "explicit length checks". The value is
consumed by `len()` and NEVER appears in the log message. The warning text
names the field and the remediation, not the bad value.

Output:
- `triggarr/startup.py` — new module-level function `_warn_if_session_secret_short`
  immediately AFTER `check_localhost_urls` (lines 25-46), plus one call site
  inside `startup()` between `print_banner(settings)` (line 176) and the
  `if not settings.has_enabled_app:` branch (line 179). The helper runs

  apps are configured — a configuration mistake in `session_secret` is
  observable regardless of `*arr` connectivity.
- `tests/test_startup.py` — three new unit tests using the existing
  `io.StringIO + logger.add` capture pattern (lines 42-47).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| config.toml on disk → loaded Settings | Untrusted in the sense that the user may have hand-edited the file; the trust assumption is "user knows what they're doing" but the startup warning is a guardrail against accidental truncation |
| auth.session_secret → itsdangerous HMAC over signed session cookies | A short secret weakens the HMAC's resistance to brute force; SEC-04 is observability-only (no enforcement), but operator visibility enables remediation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-66-04 | Spoofing | Short session_secret (< 32 chars) weakens itsdangerous TimestampSigner HMAC, making cookie forgery more tractable | mitigate (warn) | One-shot startup WARNING with `reason=session_secret_short` (D-12 single-occurrence) + remediation hint pointing to Settings → Security regenerate flow (D-14). Not a hard fail per D-12 because hard-failing would brick the first-run setup flow before the user can regenerate. |
| T-66-04b | Information Disclosure | A warning that interpolated the secret value into the log line would leak the secret via log aggregation | mitigate (by exclusion) | D-14 message names the field, not the value; SecretStr discipline (`.get_secret_value()` only feeds `len()`, never the format string); negative grep gate enforces this |
| T-66-04c | Repudiation / Operability | Periodic re-emission of the warning would create log noise and operator fatigue, leading to ignored security signals (alarm fatigue) | accept (single emission per D-12) | Warning fires once at startup; once user fixes the secret and restarts, the warning is silent. The disabled-mode periodic warning at middleware.py:114-122 is an actively-insecure-mode reminder, a different threat class. |
| T-66-04d | Tampering | A user disabling the warning by setting `auth.method = "Disabled"` (which makes auth.session_secret effectively unused) would still see the warning — false positive | accept | Code reads `if auth.needs_setup` (guard), not `if auth.is_disabled`. Disabled mode does NOT skip the warning because: (a) the user may toggle back to Forms/Basic without rotating the secret, (b) the warning naming the field is harmless when the field is unused. Skipping for Disabled would add a code path that could mask a misconfiguration. |
