<objective>
Harden the Basic auth header decode path in
`triggarr/web/middleware.py:_handle_basic_auth` (lines 157-188) by adding an
explicit control-character rejection between `base64.b64decode(...).decode("utf-8")`
(line 165) and the `secrets.compare_digest(...)` comparison (line 167). Any
character whose ordinal is in 0x00..0x1F or equals 0x7F triggers a 401 with
`WWW-Authenticate: Basic realm="Triggarr"` and a structured WARNING log line
`event=basic_auth_rejected reason=control_char client_ip=<host>`. The same
structured WARNING is also emitted on the previously-silent
`except (ValueError, UnicodeDecodeError): pass` branch (line 183-184) with
`reason=decode_failure`.

Purpose: SEC-03. Today, the decode path silently swallows base64 / UTF-8
errors and gives no operator visibility into malformed Authorization headers.
Worse, characters like NUL (0x00) reach the `secrets.compare_digest` and
`verify_password` (bcrypt) layers, where historical implementations have had
quirks. The fix is conservative — reject only control-char range (per D-09),
not all non-ASCII — so legitimate non-ASCII Unicode passwords still work.

Per D-10 (PII minimization): the WARNING never logs the decoded username, the
decoded credential bytes, or the raw Authorization header. Only `reason` and
`client_ip` (from `request.client.host` with a None-guard per Pitfall 2) are
logged.

Output:
- `triggarr/web/middleware.py` — new module-level `_has_control_chars(s: str) -> bool`
  helper, plus two new branches in `_handle_basic_auth`: the control-char check
  (between current lines 166 and 167) and a WARNING in the existing
  decode-failure except branch.
- `tests/test_auth_middleware.py` — five new tests covering null byte, control
  char, DEL, decode failure logging, and a non-ASCII password acceptance regression.
