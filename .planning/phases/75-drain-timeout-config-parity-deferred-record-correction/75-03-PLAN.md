<objective>
Refactor the scheduler shutdown drain so the timeout is resolved from the configured value at
shutdown time with the env var overriding it (D-04/D-05/D-06), delivering the precedence half of
CFG-04. This is the one real wiring change in the phase: (1) make `_read_shutdown_drain_timeout`
accept a `configured` default and apply `TRIGGARR_SHUTDOWN_DRAIN_TIMEOUT` on top with a `>= 1.0`
clamp on both sources, and (2) resolve a single local `drain` at the top of the shutdown-drain
block and replace every `_SHUTDOWN_DRAIN_TIMEOUT` reference in the shutdown path with it.

The refactor is behavior-preserving for the shutdown mechanism (`asyncio.timeout()`, WR-01) —
only the timeout VALUE source changes. The full existing suite must stay green.

Purpose: Remove the import-time-staleness footgun (the drain was read once at module import) so
the operator's configured value (and env override) is honored at actual shutdown time, where
`app.state.settings` is already in scope.
Output: A config-aware helper, a local-resolved `drain` in the shutdown block, precedence-matrix
tests, and a migrated holder-identity test.
</objective>

From triggarr/search/scheduler.py — current helper (scheduler.py:58-75):
```python
def _read_shutdown_drain_timeout() -> float:
    raw = os.environ.get("TRIGGARR_SHUTDOWN_DRAIN_TIMEOUT", "60.0")
    try:
        value = float(raw)
    except (ValueError, TypeError):
        value = 60.0
    return max(value, 1.0)
```
Target signature: `def _read_shutdown_drain_timeout(configured: float = 60.0) -> float`.
Behavior: read TRIGGARR_SHUTDOWN_DRAIN_TIMEOUT; if unset, use `configured`; if set, env wins
(coerce via float(), falling back to `configured` on (ValueError, TypeError)); return
`max(value, 1.0)` so the clamp applies to BOTH sources. Keep the existing stop_grace_period
deployment-guidance docstring tail.

|----------|-------------|
| env var / config → drain resolution | operator-supplied TRIGGARR_SHUTDOWN_DRAIN_TIMEOUT and the persisted config value cross into the shutdown timeout |
| app.state.settings → shutdown block | the typed config is read at shutdown to bound the drain wait |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-75-07 | Denial of Service | drain resolution (both sources) | mitigate | `max(value, 1.0)` clamps BOTH the configured value and the env override; a 0/negative/malformed value cannot disable the drain — the in-flight search cycle still gets a bounded grace window before SIGKILL |
| T-75-08 | Denial of Service | malformed env var at shutdown | mitigate | A non-float TRIGGARR_SHUTDOWN_DRAIN_TIMEOUT falls back to the configured default (caught via (ValueError, TypeError)) instead of crashing the shutdown path |
| T-75-09 | Tampering | app.state.settings read at shutdown | accept | FLAG 2 confirmed: app.state.settings is bound at lifespan startup (scheduler.py:473) before shutdown; no untrusted mutation path between bind and read; closure `settings` var is an equivalent in-scope read |
| T-75-10 | Information Disclosure | shutdown drain logging | accept | The drain logs the timeout value and the holder job_id/elapsed only — no token/hash/secret/PII; SecretStr discipline unaffected (no secret fields in scope) |
| T-75-SC | Tampering | npm/pip/cargo installs | accept | No new packages installed; reuses os.environ, asyncio.timeout (stdlib), and the existing scheduler shutdown path |
</threat_model>
