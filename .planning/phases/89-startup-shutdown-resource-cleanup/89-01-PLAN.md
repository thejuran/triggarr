<objective>
Give `triggarr/search/scheduler.py` one shared, non-raising, time-capped close primitive and use it in the existing shutdown `finally:` block so that one *arr client failing to close never stops the remaining clients or the database from closing, and the failure is logged sanitized.

Feature: today shutdown step 3 is a bare double `for` loop awaiting `client.close()` and step 4 is an unguarded `await app.state.db.close()` (`scheduler.py:747-755`). Any exception from one close aborts every later close and leaks the aiosqlite worker thread. This plan adds `_CLEANUP_STEP_TIMEOUT`, `_ABANDONED_CLOSE_TASKS`, `_safe_close`, `_safe_stop_scheduler`, and wires them into the shutdown path only. Plan 89-02 reuses the same helpers for the failed-startup path.

Purpose: LIFE-02 (locked decisions D-01, D-02, D-04, D-07, D-08, D-09, D-10 in 89-CONTEXT.md).

Why the catch is broad (D-07, research Pitfall B, corrected): D-07 locks a broad `Exception` catch. TEST-04 (`tests/test_clients.py:190-203`) does NOT show `close()` raising: it shows `close()` returning cleanly within milliseconds while the `AssertionError` surfaces on the in-flight request task. What it establishes is that failures around an in-flight close are not httpx-typed, so nothing guarantees a failing `close()` raises an `httpx.HTTPError` subclass (transport and OS-level errors are possible). The synthetic "close raises AssertionError" tests in this plan prove only that `_safe_close`'s catch is broad and that later steps continue; they do not reproduce TEST-04 and must not be described as doing so.

Why the cap is not `async with asyncio.timeout(...): await close_fn()` (D-09, research Pitfall E, corrected; verified against the installed source and by a probe on 2026-11-18): `aiosqlite.Connection.close()` (`core.py:199-214`) awaits a second future in its own `finally:` (`future = self.stop(); if future: await future`). When the timeout cancels the first await, that `finally:` keeps waiting on the blocked worker thread, so the awaiting task cannot finish and the `asyncio.timeout` block cannot exit. Probe result with a blocked worker and a 0.2s cap: the `asyncio.timeout` form had not returned after 1.5s; `asyncio.wait({task}, timeout=0.2)` on an owned task returned at 0.2s. `_safe_close` therefore runs the close in a task it owns, bounds only its own wait, and explicitly owns any task that outlives the cap. `asyncio.wait` is not `asyncio.wait_for` (it never cancels on timeout), so the WR-01 objection does not apply.

Output: updated `triggarr/search/scheduler.py` and `tests/test_scheduler.py`; RED/GREEN(/REFACTOR) commits per task.

Evidence-separation rule for every lifespan-driving test in this phase (both plans): tests never assert inside a `finally:` and never run rescue cleanup before capturing evidence. They call the shared helper `_observe_lifespan` (defined in Task 2), which works in three strictly ordered stages: (1) DRIVE the lifespan in an owned task under a deadline; (2) OBSERVE, without asserting or raising, the propagated exception, scheduler state (whether it is running and whether and how its shutdown was called, both snapshotted before rescue can call shutdown itself), every tracked client's closed flag, every aiosqlite worker thread's liveness and the captured log lines; (3) RESCUE, unconditionally and exception-safely, every acquired resource and the log sink. The test then asserts only against the returned observation. This keeps a failing run from replacing the injected exception, from skipping later cleanup, from passing because the test closed a client itself, and from leaving a non-daemon thread that hangs pytest at interpreter exit.
