<objective>
Make `create_lifespan`'s setup section release everything it acquired when any step fails: wrap the whole acquisition section (from `aiosqlite.connect` through the post-start `update_check` add_job) in one `try/except Exception`, track the database connection and every constructed client as plain locals, and on failure log the cause first, stop the scheduler if it is actually running, close every client, close the database, log one summary line, and re-raise the original exception unchanged.

Feature: today `lifespan` (`scheduler.py:479-668`) has no exception handling before `yield`; the `try: yield / finally:` only covers shutdown. A failed migration, cutover, client construction or scheduler start leaks the aiosqlite connection, whose non-daemon worker thread keeps the process alive until Docker's 90s SIGKILL on every restart of a crash loop (research Pitfall 6 / A). This plan reuses `_safe_close`, `_safe_stop_scheduler`, `_CLEANUP_STEP_TIMEOUT` and the `_observe_lifespan` test helper from plan 89-01.

Purpose: LIFE-01, LIFE-03 (locked decisions D-01, D-02, D-03, D-05, D-06, D-09, D-10, D-11, D-12 in 89-CONTEXT.md). Research Pitfall D: never register raw close callbacks with AsyncExitStack; every step goes through the non-raising helpers so the original exception is the one that propagates.

Log chronology (D-05, D-06): the except branch's FIRST statement logs the cause; cleanup WARNINGs follow; the summary is last; then a bare `raise`. Without the explicit cause line the first thing an operator would see for a stage that raises without logging is a cleanup warning, and the real cause would only appear afterwards in the server's own traceback. Both ERROR lines go through `_sanitize_exc`.

Scheduler state (LIFE-03, research Pitfall C as corrected; verified against the installed apscheduler 3.11.3 source and by a probe on 2026-11-18): `BaseScheduler.start()` assigns `self.state = STATE_RUNNING` at `base.py:213` and only then logs, dispatches its start event and calls `self.wakeup()` (214-218), so `start()` raising does not prove the scheduler is stopped, and a flag set after `start()` returns would miss that case. `AsyncIOScheduler.shutdown()` (`asyncio.py:40-50`) only queues the real shutdown on the event loop: probe result, `running` is still True when `shutdown()` returns and becomes False after one loop iteration. Cleanup therefore reads `scheduler.running`, requests the stop, yields one loop iteration, and re-reads `scheduler.running` before claiming the scheduler was stopped.

Task split (deliberate, so both REDs are honest): Task 1 logs the cause, closes clients and the database and re-raises, and its GREEN must NOT touch the scheduler at all. Task 2 then adds the scheduler handling; its RED tests fail against Task 1's code because a running scheduler is not stopped.

RED evidence rule (D-01, both tasks): RED runs list every new test by explicit node ID, never use `-x`, and the SUMMARY records only outcomes actually observed in that run's output. Pitfall A rule: every failed-startup test must fail pre-fix at a positive cleanup assertion, never only on exception propagation; if a test's pre-fix failure is anything else, STOP and fix the test.

Evidence-separation rule (same contract as plan 89-01): every test in this plan drives the lifespan through `_observe_lifespan`, which captures the propagated exception, scheduler state (`scheduler_running` and `scheduler_shutdown_wait`), every tracked client's closed flag, worker-thread liveness and the log lines BEFORE its unconditional, exception-safe rescue cleanup, and tests assert only on the returned `_LifespanObservation`. No `pytest.raises` around the lifespan, no assertion inside a `finally:`, no test-side `aclose()` before evidence is captured. Whether the scheduler was shut down is asserted only through the snapshots `obs.scheduler_running` and `obs.scheduler_shutdown_wait`, never through `fake.shutdown_wait` read after the helper returns: rescue calls `shutdown(wait=False)` on a scheduler still running, and `_FakeScheduler.shutdown` assigns `shutdown_wait` directly (`tests/test_scheduler.py:1964-1965`), so the live attribute reads False after rescue even when the code under test never stopped the scheduler.
