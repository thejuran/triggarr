<objective>
Add `POST /api/refresh-counts/{app}/{instance}` to `triggarr/web/routes.py` as a structural copy of `search_now` (routes.py:881) with the `_run_one_cycle` call replaced by a direct per-app `refresh_*_counts` helper call, the `last_search_time` rate-limit dict replaced by a sibling `last_refresh_time` dict, and the `last_run`/SAFETY-03-failure-counter semantics dropped. Initialize `app.state.last_refresh_time = {}` in the scheduler lifespan (alongside `last_search_time`) and in the `test_app` fixture.

The Plan 01 codex revision made `refresh_*_counts` return a 3-tuple `(filtered_missing, raw_cutoff, cutoff_tag_id)`. This endpoint is UNAFFECTED because it DISCARDS the helper return — it `await`s the helper purely for its side effect (the in-place count mutation on `state[app][instance]`) and builds the card from that mutated `ist` via `_build_app_context`. The endpoint must NOT unpack or inspect the helper result; doing so would couple it to the helper's return shape (the second codex pass flagged that the old test mocked a 2-tuple, which would mask an accidental `missing, cutoff = await refresh_fn(...)` unpack regression).

**Rewrite-3 (the third codex pass's [high] finding):** the count helper now returns None — never raises — on BOTH a fetch failure AND a malformed-nested-upstream-data fault. Plan 01 hardened the helper so that a malformed nested record (a Sonarr cutoff record with a non-dict `series`, a Radarr/Lidarr item with a non-iterable `tags`, etc.) that would otherwise raise `AttributeError`/`KeyError`/`TypeError` during the helper's filter/dedup/tag phase is now caught INSIDE the helper, treated as an upstream-data failure (connected=False + unreachable_since), and surfaced as a `None` return. That matters here because those shape-exception types are OUTSIDE this endpoint's `(httpx.HTTPError, pydantic.ValidationError, aiosqlite.Error, OSError)` catch tuple — before the helper hardening, such a fault would have propagated uncaught and produced a 500 (NOT the promised always-200 card). With the helper hardening in place, the endpoint's EXISTING None-handling already covers the data-fault path: the await is a bare statement, the card is built from the (now disconnected) `ist` state, and the endpoint returns 200 + the disconnected card. This plan does NOT change the endpoint logic for this — it ADDS a route-level regression proving the always-200 contract holds when the helper hits malformed cutoff data, and confirms the endpoint builds + returns 200 from the None path. The route catch tuple stays as-is, now functioning as a backstop rather than the primary data-fault path.

Purpose: Expose the count-only refresh as a documented, stable HTTP surface for scripts and the UI button, mirroring `search_now`'s guards, rate-limit, lock, and card-partial response (CNT-04), while structurally bypassing the scheduled-search failure counter (CNT-03), and proving the endpoint stays always-200 even when the helper hits malformed upstream data.
Output: New `refresh_counts` route; sibling `last_refresh_time` state init; new route tests (incl. the malformed-cutoff-data always-200 regression) + `refresh_test_app`/`refresh_client` fixtures in `tests/test_refresh_counts.py`; `test_app` fixture updated in `tests/test_web.py`.
</objective>
