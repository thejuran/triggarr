<objective>
Extract the shared fetch → raw-count → health → tag → filter → eligible/searchable-count work out of each `run_*_cycle` in `triggarr/search/engine.py` into three per-app helpers — `refresh_radarr_counts`, `refresh_sonarr_counts`, `refresh_lidarr_counts` — and refactor the three cycle functions to call their helper, WITHOUT changing the cycle's operation order.

This is the engine foundation for the whole phase. The structural cursor guarantee (CNT-02) is established here: `slice_batch` and every cursor/`last_run`/`last_success` write stay EXCLUSIVELY in the cycle function, so any caller of the helper alone (the Plan 02 endpoint) cannot advance the cursor or stamp run times.

**Behavior-preservation is the hard contract.** A codex adversarial review of the original draft caught a real flaw: the original helper returned a fully-filtered cutoff list, which would have forced cutoff filtering/dedup to run AHEAD of the missing-queue search. Today the cycle runs missing-filter → missing-SEARCH → cutoff-filter → cutoff-SEARCH (Radarr lines 396-455, Sonarr 639-700, Lidarr 891-946). Moving cutoff filtering before the missing search would silently change partial-failure boundaries: a malformed/huge cutoff payload could raise during cutoff dedup BEFORE the missing searches that today complete first. The existing `test_search.py` tests assert only final call counts and cursor values — NOT operation ordering — so they would stay green while real behavior drifted. This plan adopts codex's option (a): keep the cycle's operation order byte-for-byte identical.

Purpose: Make accurate counts available without a search, while keeping the scheduled search path behavior- AND order-identical (CNT-01).
Output: Three helpers + three refactored cycles in `engine.py`; new `tests/test_refresh_counts.py` with RED-first engine helper tests AND an ordering/partial-failure regression test; `tests/test_search.py` stays green.
</objective>

Corrected helper return contract (BINDING — supersedes RESEARCH Focus Point 2 / PATTERNS):
  On success the helper returns a 3-tuple: (filtered_missing, raw_cutoff, cutoff_tag_id).
    - filtered_missing: the fully-filtered missing list, ready for the cycle's missing
      slice_batch. The cycle consumes this directly. Filtering missing before the first
      slice is what the cycle already does today (pre-slice), so reusing it is safe and
      order-preserving.
    - raw_cutoff: the UNFILTERED cutoff list exactly as fetched (so the cycle does NOT
      re-fetch — single fetch preserved — but ALSO does its own cutoff filtering inline
      AFTER the missing search, exactly where it does today). The helper does NOT hand the
      cycle a pre-filtered cutoff list, because consuming a pre-filtered cutoff list would
      move cutoff filtering ahead of the missing search.
    - cutoff_tag_id: the resolved cutoff tag id (or None) so the cycle's inline cutoff
      filter applies the identical tag filter the cycle applies today.
  On fetch failure the helper returns None (after setting connected=False + unreachable_since,
  mirroring the cycle's current abort branch).

  Count-field caching is FULL inside the helper: the helper filters BOTH missing and cutoff
  on its own LOCAL copies purely to compute and cache every count field
  (missing_count, cutoff_count, missing_eligible, missing_monitored, and for Sonarr
  missing_searchable AND cutoff_searchable). The cutoff filtering the helper does internally
  is ONLY to populate counts (Sonarr cutoff_searchable); it does NOT leak a filtered cutoff
  list out to the cycle. The cycle re-filters the raw_cutoff list inline (idempotent — the
  filter primitives are pure functions of the raw list + cutoff_tag_id), so the same
  cutoff_searchable value is recomputed at the same point in the cycle as today.

Why this is provably order-preserving:
  - The cycle slices filtered_missing first → missing SEARCH runs first (unchanged).
  - The cycle then filters raw_cutoff inline → cutoff SEARCH runs second (unchanged).
  - The helper's internal cutoff filtering happens during the count-caching phase, but its
    result is NOT consumed by the cycle's search path — the cycle re-derives the cutoff list
    from raw_cutoff. So the only place a cutoff-side filtering/dedup fault can manifest on the
    SEARCH path is the cycle's inline cutoff block, which is AFTER the missing search — exactly
    as today. (The helper's internal cutoff filtering operates on already-validated client
    output and is wrapped by the same fetch try; it cannot introduce a new pre-missing failure
    mode because the fetch — the only network step — already happened together for both lists.)
