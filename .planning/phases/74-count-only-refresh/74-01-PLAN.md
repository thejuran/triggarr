<objective>
Add three NEW standalone count-only helpers — `refresh_radarr_counts`, `refresh_sonarr_counts`, `refresh_lidarr_counts` — to `triggarr/search/engine.py`. Each helper does the full fetch → raw-count → health → tag → filter → eligible/searchable-count work for one app and caches ALL count fields in the per-instance state dict in place. These helpers exist ONLY for the Plan 02 count endpoint; the scheduled `run_*_cycle` functions do NOT call them.

This is the engine foundation for the whole phase. The structural cursor guarantee (CNT-02) is established here: the helper never calls `slice_batch` and never writes any cursor / `last_run` / `last_success` field, so the count endpoint — which calls only the helper — cannot advance the cursor or stamp run times.

**The hard contract is: do NOT change the scheduled cycle's control flow or failure ordering.** Three successive codex adversarial reviews caught real flaws in earlier drafts:

1. The first draft had the helper return a fully-filtered cutoff list, which would have forced cutoff filtering/dedup to run AHEAD of the missing-queue search.
2. The first FIX returned a raw (unfiltered) cutoff list so the cycle's *consumed* list no longer reordered — BUT the helper still COMPUTED Sonarr `cutoff_searchable` by running `filter_sonarr_episodes → optional tag filter → deduplicate_to_seasons` INSIDE the helper, and `run_sonarr_cycle` `await`ed that helper BEFORE its missing search. Because `PaginatedResponse.records` is validated only as `list[dict[str, Any]]` (see `triggarr/models/arr.py`), nested cutoff shapes (a `series` dict, `seasonNumber`) are NOT schema-validated, so a malformed cutoff payload could raise during the helper's in-line cutoff dedup — BEFORE the cycle's missing searches that today complete first. The rewrite-2 fix fully DECOUPLED the helper from the cycle so no cutoff work runs before the missing search.
3. (THIS revision — rewrite-3) The third codex pass found a NEW class: the helper's OWN count path is not hardened against the SAME malformed-nested-record fault. `refresh_sonarr_counts` runs `deduplicate_to_seasons` (which does `ep.get("series", {}).get("title", ...)` — `AttributeError` if `series` is a non-dict), `filter_by_tag` over `_sonarr_tags`/`_lidarr_tags`/`_radarr_tags` (nested `.get` / membership → `AttributeError`/`TypeError`), etc. Those exception classes are OUTSIDE the route's catch tuple `(httpx.HTTPError, pydantic.ValidationError, aiosqlite.Error, OSError)`. So a malformed cutoff/tag record would raise `AttributeError`/`KeyError`/`TypeError` inside the helper, propagate uncaught to the endpoint, and produce a 500 (NOT the promised always-200 card) — possibly after a partial count mutation on `ist`. THIS plan hardens the helper count path against that: a narrow `(AttributeError, KeyError, TypeError)` catch around the filter/dedup/tag phase treats malformed nested data as an upstream-DATA failure (connected=False + unreachable_since + return None — the same disconnected outcome as a fetch failure, extending D-04), with count fields committed to `ist` only after their inputs filter successfully so no half-updated count set is left behind.

**Scope guard (UNCHANGED from rewrite-2):** This hardening is in the HELPER count path ONLY. The `run_*_cycle` bodies stay byte-for-byte unchanged — the cycle's existing malformed-data behavior is pre-existing and OUT OF SCOPE for this phase. Do NOT touch the cycle bodies.

This revision keeps the decoupled design that provably eliminates the pre-missing-search-failure class: **the count helper is fully decoupled from the cycle.** The `run_*_cycle` functions keep their ENTIRE existing body unchanged — same missing filter, same missing search loop, same cutoff dedup AFTER the missing search at the same lines, same `ist["cutoff_searchable"]` write in the cutoff block. The cycle does NOT delegate its cutoff (or missing) computation to the helper and does NOT await any helper work before the missing search. The helper is a separate count path that the cycle never touches. Net effect to verify: a `git diff` of each `run_*_cycle` shows NO new pre-missing-search `await`/filter/dedup that was not there before; the cutoff block stays where it is.

Purpose: Make accurate counts available without a search (the Plan 02 endpoint path), while keeping the scheduled search path's control flow and failure boundaries byte-for-byte identical to today (CNT-01), AND guaranteeing the helper never leaks a shape/data exception that would turn the always-200 count endpoint into a 500.
Output: Three NEW standalone count-only helpers in `engine.py`, each hardened against malformed nested records; `run_*_cycle` control flow unchanged; new `tests/test_refresh_counts.py` with RED-first helper unit tests (incl. malformed-nested-data fault tests) AND per-app (Radarr/Sonarr/Lidarr) search-call-order + cutoff-fault-before-missing regression tests; `tests/test_search.py` stays green.
</objective>

Decoupled count-only helper contract (BINDING — supersedes RESEARCH Focus Point 2 / PATTERNS
AND the earlier first-fix draft):
  - The helper is a STANDALONE count path. It is used ONLY by the Plan 02 count endpoint.
    The run_*_cycle functions do NOT call it.
  - On success the helper does the FULL work for one app: fetch missing+cutoff once → best-effort
    library count → set connected=True / unreachable_since=None → cache missing_count/cutoff_count/
    total_items → resolve tags (honoring get_tags_fn) → run the missing filter chain and cache
    missing_eligible (+ missing_monitored for Radarr/Lidarr, + missing_searchable for Sonarr) →
    run the cutoff filter chain on a local copy and, for Sonarr, cache cutoff_searchable. Order
    among these is IRRELEVANT inside the helper because there is NO missing search to protect in
    the count path — there is no search loop here at all.
  - FAILURE CONTRACT (rewrite-3, extends D-04): the helper NEVER raises an uncaught exception to its
    caller. TWO disconnected fault paths, both → set connected=False + unreachable_since + return None:
      (a) FETCH failure: the fetch await is wrapped in the SAME tuple the cycle uses for its abort
          branch (httpx/pydantic — the cycle's existing fetch-abort tuple; mirror it exactly).
      (b) DATA failure: the filter/dedup/tag phase (everything that touches nested record shapes —
          tag resolution+filter_by_tag, filter_sonarr_episodes/deduplicate_to_seasons,
          filter_monitored/filter_unreleased_movies) is wrapped in a narrow `(AttributeError,
          KeyError, TypeError)` catch. On such a shape fault the helper logs (via _sanitize_exc /
          str split as appropriate), flips to disconnected, and returns None.
  - NO-PARTIAL-STATE on the data-fault path: count fields (missing_count/cutoff_count are raw and may
    be set before filtering, but the EEligible/searchable fields — missing_eligible/missing_monitored/
    missing_searchable/cutoff_searchable) must be committed to ist ONLY after their inputs successfully
    filter. Structure the helper so that if the filter/dedup phase raises, the disconnected reset
    leaves NO half-updated eligible/searchable set (either compute all eligible/searchable locally and
    assign to ist at the end of a successful filter phase, OR on the data-fault path reset the
    eligible/searchable fields as part of the disconnected outcome). The acceptance test asserts no
    half-updated count set on the fault path.
  - The helper writes ALL count fields in place on ist = state[app][instance_name]. The count
    endpoint reads those fields off ist to build the card; it DISCARDS the helper's return value.
  - The documented return type is the 3-tuple (filtered_missing, raw_cutoff, cutoff_tag_id) | None
    purely for a stable, typed signature and possible future reuse. NO caller unpacks or inspects
    it. The 3-tuple shape exists so a test that mocks the helper with a 3-tuple return passes
    cleanly through the endpoint (see Plan 02). On fetch failure OR data failure the helper returns
    None.
  - The helper NEVER calls slice_batch and NEVER writes missing_cursor/cutoff_cursor/last_run/
    last_success (structural CNT-02/CNT-03).

The run_*_cycle functions (BINDING — leave control flow unchanged):
  - Do NOT call any refresh_*_counts helper.
  - Keep their ENTIRE existing body byte-for-byte: same missing filter chain, same missing search
    loop + missing_cursor write, same cutoff filter/dedup INLINE AFTER the missing search, same
    cutoff search loop + cutoff_cursor write, same ist["cutoff_searchable"] write (Sonarr) in the
    cutoff block, same diagnostic + last_run/last_success. The cycle's existing (pre-existing,
    unchanged) malformed-data behavior is OUT OF SCOPE for this phase — do NOT add the new
    narrow-tuple catch to the cycle.
  - The ONLY edits permitted in this plan to engine.py are: (a) ADDING the three new helper
    functions (each with the fetch-fault AND data-fault catches), and (b) leaving everything else
    identical. A git diff of run_radarr_cycle / run_sonarr_cycle / run_lidarr_cycle must show ZERO
    changes to their bodies.

Why this is provably order- and failure-boundary preserving:
  - The cycle's control flow is untouched, so missing-filter → missing-SEARCH → cutoff-filter/dedup
    → cutoff-SEARCH stays byte-for-byte. No cutoff filtering/dedup runs before the missing search.
  - The helper does cutoff filtering/dedup, but only inside the count-only path that has no missing
    search to gate — so a malformed-cutoff fault there can only affect a count refresh, never a
    scheduled missing search. AND that fault is now CAUGHT in the helper (narrow tuple) and turned
    into a disconnected+None outcome, so the count endpoint stays always-200.
  - Some code duplication between helper and cycle (both run the same filter chains) is the
    deliberate, accepted cost of guaranteeing the scheduled search path's failure ordering is
    identical to today. D-02 is still honored: helper and cycle call the SAME shared primitives,
    so the filter SEQUENCE cannot drift even though the call sites are separate.
