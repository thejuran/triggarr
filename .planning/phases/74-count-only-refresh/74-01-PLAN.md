<objective>
Add three NEW standalone count-only helpers — `refresh_radarr_counts`, `refresh_sonarr_counts`, `refresh_lidarr_counts` — to `triggarr/search/engine.py`. Each helper does the full fetch → raw-count → health → tag → filter → eligible/searchable-count work for one app and caches ALL count fields in the per-instance state dict in place. These helpers exist ONLY for the Plan 02 count endpoint; the scheduled `run_*_cycle` functions do NOT call them.

This is the engine foundation for the whole phase. The structural cursor guarantee (CNT-02) is established here: the helper never calls `slice_batch` and never writes any cursor / `last_run` / `last_success` field, so the count endpoint — which calls only the helper — cannot advance the cursor or stamp run times.

**The hard contract is: do NOT change the scheduled cycle's control flow or failure ordering.** Two successive codex adversarial reviews caught real flaws in earlier drafts:

1. The first draft had the helper return a fully-filtered cutoff list, which would have forced cutoff filtering/dedup to run AHEAD of the missing-queue search.
2. The first FIX returned a raw (unfiltered) cutoff list so the cycle's *consumed* list no longer reordered — BUT the helper still COMPUTED Sonarr `cutoff_searchable` by running `filter_sonarr_episodes → optional tag filter → deduplicate_to_seasons` INSIDE the helper, and `run_sonarr_cycle` `await`ed that helper BEFORE its missing search. Because `PaginatedResponse.records` is validated only as `list[dict[str, Any]]` (see `triggarr/models/arr.py`), nested cutoff shapes (a `series` dict, `seasonNumber`) are NOT schema-validated, so a malformed cutoff payload could raise during the helper's in-line cutoff dedup — BEFORE the cycle's missing searches that today complete first (Sonarr missing search 639-692, cutoff dedup 695-700). That is the SAME pre-missing-failure class as the original flaw, surviving via the count-computation path. A pure search-call-order test would NOT catch it, because search calls can still be missing-first while cutoff FILTERING/dedup has already moved earlier and raised.

This revision adopts the only design that provably eliminates the class: **the count helper is fully decoupled from the cycle.** The `run_*_cycle` functions keep their ENTIRE existing body unchanged — same missing filter, same missing search loop, same cutoff dedup AFTER the missing search at the same lines, same `ist["cutoff_searchable"]` write in the cutoff block. The cycle does NOT delegate its cutoff (or missing) computation to the helper and does NOT await any helper work before the missing search. The helper is a separate count path that the cycle never touches. Net effect to verify: a `git diff` of each `run_*_cycle` shows NO new pre-missing-search `await`/filter/dedup that was not there before; the cutoff block stays where it is.

Purpose: Make accurate counts available without a search (the Plan 02 endpoint path), while keeping the scheduled search path's control flow and failure boundaries byte-for-byte identical to today (CNT-01).
Output: Three NEW standalone count-only helpers in `engine.py`; `run_*_cycle` control flow unchanged; new `tests/test_refresh_counts.py` with RED-first helper unit tests AND per-app (Radarr/Sonarr/Lidarr) search-call-order + cutoff-fault-before-missing regression tests; `tests/test_search.py` stays green.
</objective>

Decoupled count-only helper contract (BINDING — supersedes RESEARCH Focus Point 2 / PATTERNS
AND the earlier first-fix draft):
  - The helper is a STANDALONE count path. It is used ONLY by the Plan 02 count endpoint.
    The run_*_cycle functions do NOT call it.
  - On success the helper does the FULL work for one app: fetch missing+cutoff once → best-effort
    library count → set connected=True / unreachable_since=None → cache missing_count/cutoff_count/
    total_items → resolve tags (honoring get_tags_fn) → run the missing filter chain and cache
    missing_eligible (+ missing_monitored for Radarr/Lidarr, + missing_searchable for Sonarr) →
    run the cutoff filter chain on a local copy and, for Sonarr, cache cutoff_searchable. Order
    among these is IRRELEVANT inside the helper because there is NO missing search to protect in
    the count path — there is no search loop here at all.
  - The helper writes ALL count fields in place on ist = state[app][instance_name]. The count
    endpoint reads those fields off ist to build the card; it DISCARDS the helper's return value.
  - The documented return type is the 3-tuple (filtered_missing, raw_cutoff, cutoff_tag_id) | None
    purely for a stable, typed signature and possible future reuse. NO caller unpacks or inspects
    it. The 3-tuple shape exists so a test that mocks the helper with a 3-tuple return passes
    cleanly through the endpoint (see Plan 02). On fetch failure the helper returns None (after
    setting connected=False + unreachable_since, mirroring the cycle's current abort branch).
  - The helper NEVER calls slice_batch and NEVER writes missing_cursor/cutoff_cursor/last_run/
    last_success (structural CNT-02/CNT-03).

The run_*_cycle functions (BINDING — leave control flow unchanged):
  - Do NOT call any refresh_*_counts helper.
  - Keep their ENTIRE existing body byte-for-byte: same missing filter chain, same missing search
    loop + missing_cursor write, same cutoff filter/dedup INLINE AFTER the missing search, same
    cutoff search loop + cutoff_cursor write, same ist["cutoff_searchable"] write (Sonarr) in the
    cutoff block, same diagnostic + last_run/last_success.
  - The ONLY edits permitted in this plan to engine.py are: (a) ADDING the three new helper
    functions, and (b) leaving everything else identical. A git diff of run_radarr_cycle /
    run_sonarr_cycle / run_lidarr_cycle must show ZERO changes to their bodies.

Why this is provably order- and failure-boundary preserving:
  - The cycle's control flow is untouched, so missing-filter → missing-SEARCH → cutoff-filter/dedup
    → cutoff-SEARCH stays byte-for-byte. No cutoff filtering/dedup runs before the missing search.
  - The helper does cutoff filtering/dedup, but only inside the count-only path that has no missing
    search to gate — so a malformed-cutoff fault there can only affect a count refresh, never a
    scheduled missing search.
  - Some code duplication between helper and cycle (both run the same filter chains) is the
    deliberate, accepted cost of guaranteeing the scheduled search path's failure ordering is
    identical to today. D-02 is still honored: helper and cycle call the SAME shared primitives,
    so the filter SEQUENCE cannot drift even though the call sites are separate.
