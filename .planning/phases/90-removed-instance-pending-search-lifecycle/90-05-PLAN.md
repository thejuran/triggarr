Planner findings and decisions (beyond 90-RESEARCH.md):
- **Second removal path.** `save_settings` (routes.py ~725-870) treats the submitted form as the full instance list for an app, so an instance missing from the form is removed (pinned by `test_save_settings_form_removal_invalidates_tag_cache`). The form keeps an existing instance's stable ID by name and gives a new name a new ID, so "removed" there means: a stable ID present in the old settings of that app and absent from the new settings. This path gets the same close-out.
- **Placement in `remove_instance`: last step inside the lock, after the synchronous tidy-up.** The close-out is the only awaited tidy-up step inside the lock. Placing it after the scheduler-job removal and the three dict pops means a cancellation arriving during it cannot skip them (Phase 87 D-16). Research suggested "after the settings swap"; this placement satisfies that and is stricter.
- **Placement in `save_settings`: last step inside the lock, after state persistence.** `save_settings` has two awaited steps after the settings swap (state persistence inside the lock, stale-client closes outside it). Putting the close-out after state persistence means the new awaited step can never skip state persistence; only the stale-client closes remain after it, and they are made to finish through a held cancellation (below).
- **Cancellation during the close-out.** The database function finalizes its transaction before it re-raises (plan 90-02), so by the time the route sees the `CancelledError` the connection is outside any transaction, and the route is still holding `search_lock`. In `remove_instance` the cancellation is held in the route's existing `cancelled` variable (as the write and the client close already do) so the client is still closed outside the lock; the existing re-raise at the end then lets it through. In `save_settings` it is held in a new local, the stale clients are closed through `_close_removed_client` (which finishes a close through a re-delivered cancellation), and it is then re-raised. A close-out interrupted this way is repaired by the startup sweep (plan 90-06).
- **Log safety (plan-check finding).** The redacting sink only replaces the secret values it was configured with (`triggarr/logging.py` `_redact`, lines 20-25). `save_settings` rebuilds the sink from the new settings (routes.py ~752-758, `collect_secrets` in `triggarr/startup.py` 74-100) before the close-out runs, so a removed instance's API key is no longer redacted there, and a URL with embedded credentials is never in the list. The two new error boundaries therefore never interpolate the exception text: they log `_sanitize_exc(exc)` (already imported in routes.py; `triggarr/clients/base.py` 17-33 returns the exception type name or an HTTP class), the same way plan 90-06 logs the sweep failure. The neighbouring pre-existing steps' log lines are not changed by this plan.
- **A retired connection is replaced here, inside the lock (plan-check finding, iteration 2).** Plan 90-02 guarantees that a failed or cancelled close-out leaves the connection either verified clean or retired (closed, unable to commit). The route is the owner of `app.state.db` at that moment, so it is the route that swaps in the replacement: a small helper `_replace_retired_db(app)` checks `is_connection_retired(app.state.db)` (synchronous; in the normal case it returns at once and adds no await), and otherwise obtains `replace_retired_connection(...)` as its own task waited through a shield (the `_close_removed_client` shape, so a held or re-delivered cancellation cannot abandon a half-opened connection) and assigns the result to `app.state.db`. It runs before the lock is released, because tracking and search cycles wait on that lock and read `app.state.db` when they run. D-00b is unaffected: the response and the remaining tidy-up do not depend on it, and a replacement failure is logged (sanitized) and otherwise ignored; the retired connection then stays published, every later database call on it fails rather than commits, and a restart recovers. The shutdown path closes whatever `app.state.db` holds, so the replacement is closed there; the retired one is already closed.
- **Fixture inventory, corrected (plan-check finding, iteration 2).** `multi_instance_app` (tests/test_web.py 1061-1130) configures Radarr `Default` (enabled) and `4K` (`enabled=False`) and Sonarr `Default` (enabled) in `Settings`. For Lidarr it has only a state entry (`"lidarr": {"Default": ...}`) and a mock client (`app.state.lidarr_clients["Default"]`); there is no Lidarr `InstanceConfig`. Tests that need a configured Lidarr instance add one locally to a copy of the settings. The shared fixture is not changed.
- **Queued work is not this plan's subject.** A scheduled job or manual search that was already waiting on `search_lock` when the removal ran is handled in plan 90-07 (in-lock revalidation). This plan must not add any comment claiming that rows inserted by such work are "never selected"; plan 90-07 writes the accurate comment.
