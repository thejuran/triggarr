<objective>
Turn away search work that was queued on `search_lock` for an instance that was removed (or replaced under the same name) while it waited.

Purpose: the plan checker found that the earlier treatment of this race was wrong. `make_search_job`'s `job()` (triggarr/search/scheduler.py:169-229) reads the instance's client and configuration before it waits for `search_lock`. If the instance is removed while the job waits, the job then runs a full search cycle through the removed instance's old client, records new pending searches under the removed stable ID, and immediately runs `run_tracking_check` with that same old stable ID, which selects and can credit those rows. Stable-ID selection does not protect against this, because the stale job itself carries the removed ID. `search_now` (triggarr/web/routes.py:1271-1331) has the same shape. Both removal paths leave this open: the Remove action, and Save Settings (routes.py:767-829), which additionally keeps the removed instance's state entry. Without this plan RMINST-01 and RMINST-02 can be violated seconds after a removal.
Output: one shared in-lock check in `triggarr/search/scheduler.py`, used by the scheduled job and the manual search route, with deterministic regressions for both removal paths.
</objective>

Planner decisions:
- **Rule: identity, enabled, current client.** Queued work may run only if, inside the lock, the live settings still hold an enabled instance under that name whose `id` equals the stable ID the work captured before waiting, and the live client registered under that name is the same object (`is`) the work captured. Name existence alone is not enough: an instance removed and re-created under the same name has a new stable ID and a new client, and the old queued work must not run for it. The stable IDs are compared for equality rather than required to be non-empty, because test fixtures (and only they) hold instances with an empty ID; the client-identity half of the rule still turns stale work away there.
- **Live configuration is used.** When the check passes it returns the configuration read inside the lock, and the cycle and the tracking check use that object instead of the one captured before waiting.
- **Same-ID client replacement.** If Save Settings replaced the client of a still-configured instance (changed URL or key), queued work is turned away for that one run; the scheduled job runs again at its interval and a manual search can be clicked again. Accepted: the old client has been closed, so running through it would fail anyway.
- **Response for a turned-away manual search:** the existing pre-lock answer for a missing instance, `HTMLResponse("Instance not enabled", status_code=400)`. No new user-facing text.
- **Scope:** the scheduled job and the manual search, the two entry points that record pending searches and (the job) run tracking. `refresh_counts` reads its client before the lock in the same way but records no search and credits nothing; it is left unchanged and noted in the SUMMARY as observed.
