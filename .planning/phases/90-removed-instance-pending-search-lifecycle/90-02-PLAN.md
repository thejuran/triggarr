Planner decisions recorded here (CONTEXT D-11 and the discretion list delegate them; research A1, A3, A4):
- **Rows with no stable ID (A1): closed by the sweep.** Evidence: migration v10 associated every configured (app, name) pair and every writer since passes the instance's ID, so a pending, non-Legacy row with a NULL stable ID cannot belong to a configured instance. After plan 90-03 nobody selects such rows, and pending rows are never pruned, so leaving them would keep them "in progress" forever. Closing a row is the opposite of adopting it, so D-00c holds. NULL-ID Sonarr rows are all at or below the cutover (Legacy) and stay Legacy. The few rows imported from the old state file without an item ID get the same label; they were never trackable.
- **Zero configured instances (A3, revised after plan check): the sweep runs; there is no set-size guard.** D-11 says the sweep closes pending searches whose stable ID is not a configured instance; with zero instances that is every pending, non-Legacy search. A valid configuration with zero instances is a normal state: it is what remains after the last instance is removed, including when that removal's close-out failed after the settings write (D-00b), which is exactly the case the sweep exists to repair. Evidence that an empty set never means a missing or broken configuration: `triggarr/__main__.py` `_run` calls `startup()` and only then `create_lifespan(settings, ...)`; `startup()` calls `ensure_config` (`triggarr/config.py` ~578-625), which for a missing file writes the default template and exits with code 1, and for an unreadable, corrupt or invalid file (`TOMLDecodeError`, `UnicodeDecodeError`, `ValidationError`) logs and exits with code 1. The sweep's caller therefore only ever holds a validated configuration read from the file; a missing or invalid configuration is already distinguished, upstream, by the process not starting. Known consequence, stated plainly for the SUMMARY: if Triggarr is started with a valid configuration that has no instances (for example a regenerated default file) next to an existing database, the searches still pending at that moment are closed as "Instance removed". Stable IDs exist only in the configuration file, so instances re-added by hand get new IDs and could never own those rows again; the only thing lost is tracking of those pending searches if the old file is restored afterwards.
- **Recurring check only, no migration.** A migration cannot see the cutover (recorded after migrations run) and would not repair a close-out that failed after a successful settings write (D-00b).
- **Detail text (A4):** the fixed string `instance removed`, overwriting the previous detail, as every other resolution does.
- **grab_ownership and lifetime_stats:** left untouched (D-09; no defect shown).
- **Transaction finalization under cancellation (revised after plan check).** `update_outcome_and_stats` rolls back on `Exception` only. That is not enough for the new functions: `asyncio.CancelledError` is a `BaseException`, and cancelling an awaited aiosqlite call does not cancel the statement already handed to the connection's worker thread, so an UPDATE can still be applied and stay in an open transaction on the shared connection until an unrelated operation commits it. Both new functions therefore finalize the transaction on every exit path, including cancellation, and only then re-raise. The research code example (`except Exception: await db.rollback()`) is superseded by this decision. `update_outcome_and_stats` itself is not changed by this phase; whether it shares the gap is recorded in the SUMMARY as an observation.
- **Verified rollback, and retirement when it cannot be verified (revised after plan check, iteration 2).** Awaiting a rollback is not proof that it happened: `db.rollback()` can raise (for example on an I/O error), and a rollback call that was itself cancelled may or may not have reached the connection's worker thread. Logging and returning in those cases would leave the applied UPDATE inside an open transaction on the shared connection, and plans 90-05 and 90-06 go on using that connection, so the next unrelated `commit()` would persist a close-out the caller was told had failed. The rule therefore has three steps. (1) Verify: an attempt counts as clean only when the rollback call completed without error and `db.in_transaction` read afterwards is False. `in_transaction` is read from the event-loop thread while statements run on the worker thread, so it is only trusted directly after a rollback call that completed (which was queued behind every earlier statement of this function); it is never read after a failed or cancelled attempt as a substitute for a completed rollback. (2) Retry: up to 3 attempts in total, each a new rollback call queued behind the previous one. (3) Retire: when no attempt ended verified clean, the connection is marked retired and closed. Closing a SQLite connection discards its uncommitted transaction, and aiosqlite 0.22 drops its handle in a `finally` inside `close()` even when the close itself raises, so every later call on the retired object raises instead of committing. This is the isolation: the abandoned changes cannot be persisted by anyone.
- **How the application holds the connection, and why replacement is a swap.** There is exactly one connection: `create_lifespan` opens it (`triggarr/search/scheduler.py` ~698), stores it as `app.state.db` (~752) and closes it at shutdown (~1026). Routes read `request.app.state.db` and the scheduled jobs read `app.state.db` at the moment they run (~223, ~399); nothing keeps its own long-lived reference. A retired connection is therefore replaced by assigning a new connection to that one attribute (routes, plan 90-05) or to the lifespan's local before it is published (plan 90-06). The new connection is opened by `replace_retired_connection` on the database file path that `init_db` recorded for the old one (`init_db(db, db_path)` is called for every connection the application and the test fixtures use, so no new `app.state` attribute is needed), with the same two PRAGMAs as the lifespan and `row_factory = aiosqlite.Row`; it does not run `init_db` again (the schema exists; a second run would also take a migration backup). Smallest sound mechanism: one module-level `weakref.WeakSet` of retired connections, one `weakref.WeakKeyDictionary` of connection to path, three small functions. A dedicated exception type was rejected because the cancellation path must re-raise `CancelledError` and so cannot carry it; a predicate the caller checks after any failure works on every exit path.
- **What retirement costs, stated plainly for the SUMMARY.** It needs a rollback that fails or is cancelled three times in a row, which in practice means the disk or the process is already in trouble. Work of another request that was mid-flight on the retired connection fails with an error instead of committing; that is the intended fail-closed outcome. If the close of the retired connection itself could not finish, its worker thread may still hold the write lock; the replacement then fails its writes with a lock error until restart, which is again fail-closed. D-00b is preserved by the callers: the removal response stays successful and the remaining tidy-up still runs (plan 90-05); a close-out abandoned this way is repaired by the startup sweep.
