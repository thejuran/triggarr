Planner decisions (research A2, A3; delegated by the orchestrator, not owner questions):
- **Failure policy (A2): logged, startup continues.** The sweep is repair. Safety does not depend on it: a row is only selected by a tracking check running under that row's own stable ID (plan 90-03), and work still queued for a removed instance is turned away inside the lock (plan 90-07); a failed sweep runs again at the next start. This differs on purpose from `ensure_cutover_recorded`, which stays uncaught because a missing cutover has attribution consequences. Only `Exception` is caught, so a cancellation still reaches the Phase 89 failed-startup cleanup.
- **Retired connection after a failed sweep (plan-check finding, iteration 2).** Plan 90-02 leaves the connection verified clean or retired when the sweep fails. "Startup continues" must not mean continuing on a retired connection (every later database call would fail) and must never mean continuing on one that still holds the abandoned UPDATEs (plan 90-02 rules that out by retiring it). The lifespan holds the connection in its local `db` and publishes it as `app.state.db` only later (~752), so the repair is a rebind of that local inside the failure handler: `if is_connection_retired(db): db = await replace_retired_connection(db)`. A failure to open the replacement is deliberately not caught: there is then no usable database, and startup must stop through the Phase 89 cleanup, the same way it stops when the first connection cannot be opened. The cleanup closes the local `db`; closing the already-closed retired connection is a no-op in aiosqlite, and a replacement that was opened is the local and is closed there. On cancellation nothing is replaced: the cancellation propagates and the cleanup closes whatever the local holds.
- **Zero configured instances (A3, revised after plan check): the sweep runs.** D-11 closes pending searches whose stable ID is not a configured instance; with zero instances that is every pending, non-Legacy search, and it is the state left by removing the last instance, including when that removal's close-out failed (D-00b). The lifespan cannot be reached with a missing or invalid configuration: `triggarr/__main__.py` `_run` awaits `startup()` before `create_lifespan`, and `ensure_config` (`triggarr/config.py` ~578-625) exits the process with code 1 when the file is missing (after writing the default template), unreadable, corrupt or invalid. So `settings` here is always a validated configuration read from the file, the missing/invalid case is already distinguished upstream, and neither this call site nor the database function branches on the size of the set. Consequence to state in the SUMMARY: a start with a valid configuration that has no instances (for example a regenerated default file) next to an existing database closes the searches pending at that moment as "Instance removed"; stable IDs live only in the configuration file, so instances re-added by hand could never own those rows again.
- **Slot:** immediately after `ensure_cutover_recorded`. Earlier, the cutover row may not exist, nothing would count as Legacy, and the sweep would rewrite pre-cutover Sonarr rows (research P1).
- **Configured set:** every configured instance, enabled or not; a disabled instance can be re-enabled and must keep its pending searches (research P2).

  <behavior>
    - Lifespan start with a database holding orphan pending rows: those rows are instance_removed once the lifespan has started; configured (enabled or disabled) and Legacy rows unchanged.
    - Sweep raising RuntimeError: lifespan still starts, scheduler started, one sanitized ERROR.
    - Sweep raising CancelledError: startup aborts through the existing cleanup (database closed).
    - Sweep failing with its connection retired: the lifespan starts on a new clean connection; when no replacement can be opened, startup aborts through the existing cleanup.
    - Lifespan start with `Settings()` (no instances) and a database holding pending rows: non-Legacy pending rows are instance_removed, Legacy rows unchanged.
  </behavior>
