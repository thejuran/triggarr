<objective>
Add a per-job consecutive-failure counter on `app.state.search_failures` keyed by
`f"{app_name}_{instance_name}_search"`, and escalate the failure log line from
WARNING to ERROR once the count reaches the configurable
`general.max_consecutive_failures` threshold (default 5, bounds 1..100). Wire the new
config field end-to-end: pydantic model + DEFAULT_CONFIG template + POST /settings
form handler + template context + settings.html input. The counter resets on cycle
success (independent of whether the post-cycle tracking check succeeds).

Purpose: SAFETY-03. After plan 65-01, transient external-service failures still log
identically every cycle, drowning the operator in indistinguishable WARNINGs. After
this plan, repeated failures become visually distinguishable (level escalation) and
single transient blips do not promote to ERROR.

Output:
- `triggarr/models/config.py` — new pydantic field with explicit ge=1 le=100 bounds.
- `triggarr/config.py` — new commented line in DEFAULT_CONFIG under `[general]`.
- `triggarr/search/scheduler.py` — `app.state.search_failures: dict[str, int] = {}`
  initialization in `create_lifespan`; replaced failure-log body in the narrowed
  except branch (from plan 65-01) with the increment + escalation logic; reset-on-
  success line after successful `save_state` and before the tracking-check block.
- `triggarr/web/routes.py` — `safe_int` entry in the POST /settings general dict;
  context-dict entry for the GET render.
- `triggarr/templates/settings.html` — number input copied positionally from the
  `max_history_rows` sibling.
- `tests/test_config.py` — 1 new pydantic default-value test.
- `tests/test_scheduler.py` — 4 new tests for the counter behavior (increment,
  escalation, reset, per-instance scoping).
