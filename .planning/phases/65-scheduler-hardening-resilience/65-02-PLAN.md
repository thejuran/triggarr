<objective>
Add a per-job consecutive-failure counter on `app.state.search_failures` keyed by
`f"{app_name}_{instance_name}_search"`, and escalate the failure log line from
WARNING to ERROR once the count reaches the configurable
`general.max_consecutive_failures` threshold (default 5, bounds 1..100). Wire the new
config field end-to-end: pydantic model + DEFAULT_CONFIG template + POST /settings
form handler + template context + settings.html input. The counter resets on cycle
success.

**Revision note (Codex finding 1 — SAFETY-03 counter must observe REAL outages).**
The prior draft of this plan only incremented the counter when a narrow-tuple exception
was *raised* through `make_search_job`. But the production engine cycles
(`run_radarr_cycle` / `run_sonarr_cycle` / `run_lidarr_cycle`) already catch
`httpx.HTTPError`/`pydantic.ValidationError` internally, set
`state["{app}"][instance]["connected"] = False`, and **return state** instead of
raising. Under a sustained Radarr/Sonarr/Lidarr outage, the prior counter design
NEVER incremented and the operator NEVER saw an ERROR-level escalation.

Fix direction (chosen: option **(b)** from REVIEWS.md — use cycle outcome already
encoded in returned state, no engine contract change required):

After `cycle_fn(...)` returns, inspect the instance state's `connected` field:
- `connected == False` → real outage path → increment `search_failures[job_id]`,
  log at WARNING (below threshold) or ERROR (at/above threshold).
- `connected == True` → success → reset `search_failures[job_id] = 0`.

The narrow-tuple `except` branch retained from plan 65-01 covers the *rare* case
where a cycle raises through (e.g., a future code path or `aiosqlite.Error`
escaping the engine). Both paths feed the same counter and escalation primitive.

Tests in this plan MUST drive the cycle-outcome path by mocking the client's HTTP
calls (so `run_radarr_cycle` executes for real, catches the httpx.HTTPError, marks
the instance disconnected, and returns) — NOT by patching `run_radarr_cycle` itself
to raise. The previous mock-the-cycle approach validated a synthetic path that
production never exercises.

**Revision note (Codex finding 2 — persistence failures must NOT be treated as
transient blips).** The prior draft caught `OSError` from both `cycle_fn(...)` and
`save_state(...)` in the same narrow-tuple branch. State is mutated before
`save_state` runs; a disk-full or permission failure mid-persistence would be
counted as a transient blip, the counter would only escalate at threshold, and
in-memory and durable state would diverge silently.

Fix direction:

Split cycle execution from persistence. Wrap ONLY the `save_state(...)` call in a
dedicated `try/except (OSError, aiosqlite.Error)` branch that:
- Logs at ERROR immediately (no warning/threshold gate),
- Does NOT reset the success counter (durability has degraded; treat as a hard
  failure for observability),
- Sets `app.state.persistence_degraded = True` so a follow-up health check or future
  endpoint can surface the state (this plan only sets the flag; we do not add a
  health endpoint here),
- Re-raises so APScheduler's `_on_job_error` listener (added in 65-01) also logs
  with `job_id` context. (Re-raising is safe: SAFETY-02 propagation now produces
  visible logs; the engine cycle has already returned, so there is no half-finished
  cycle to confuse.)

Purpose: SAFETY-03. After plan 65-01, transient external-service failures still log
identically every cycle, drowning the operator in indistinguishable WARNINGs. After
this plan, repeated failures become visually distinguishable (level escalation),
single transient blips do not promote to ERROR, real *arr outages are detected via
the engine's existing connection-state signal, and durability failures during
persistence are loud and separate.
