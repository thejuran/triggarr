<objective>
Extend the graceful-shutdown lock-drain timeout from 35s to a configurable
`_SHUTDOWN_DRAIN_TIMEOUT` (default 60.0s, env-overridable via
`TRIGGARR_SHUTDOWN_DRAIN_TIMEOUT`) and replace the non-actionable single-line warning
with structured warnings that name which job was holding the lock and how long it
had been running. Emit holder identity at INFO level on entry to the drain so logs
contain context even when Docker forcibly kills the process before the timeout fires.

Achieve this by extracting the timeout into a module-level constant that reads the
env var at import time (so tests can patch it to a sub-second value via
`monkeypatch.setattr`), tracking the holder identity on
`app.state.search_lock_holder: tuple[str, float] | None`, and reading the holder
inside both the start-of-drain INFO log and the `except TimeoutError:` branch.

**Revision note (Codex finding 3 — drain timeout must align with Docker deployment).**
The prior draft of this plan claimed a real `docker stop` against the project's
recommended `docker-compose.yml` would surface the holder-identity warning. It would
not. The repo's docker-compose.yml defines NO `stop_grace_period`, so Docker uses
its 10-second default, sends SIGKILL after 10 seconds, and the 60-second in-process
drain never completes. The new warning never fires; client/db cleanup is skipped.

Fix direction (chosen from REVIEWS.md):

1. **Add `stop_grace_period: 90s` to `docker-compose.yml`** — 90s = 60s drain + 30s
   margin for the subsequent client + db close steps.
2. **Document the requirement in `README.md`** — for `docker run` users (no compose),
   recommend `--stop-timeout 90`; for systemd users, mention `TimeoutStopSec=90`.
3. **Make the drain timeout configurable via `TRIGGARR_SHUTDOWN_DRAIN_TIMEOUT` env
   var** — so deployment operators can tune for their environment (e.g., lower for
   CI/test, higher for slow networks).
4. **Emit holder identity at INFO level on entry to drain** — not just on timeout —
   so the log line is present in container logs even if the SIGKILL races the
   timeout. The TimeoutError branch still fires its WARNING with elapsed time when
   the drain completes its full window in-process.

Purpose: RES-01. Today's 35s timeout fires the warning `"Shutdown: search cycle did
not finish in 35s — forcing close"` with no indication of which Radarr/Sonarr/Lidarr
instance is stuck. After this plan, the operator sees:

`Shutdown: draining search lock (timeout=60.0s); holder=radarr_4K_search elapsed=12.3s` (INFO, at entry)

and if the timeout fires:

`Shutdown: search cycle did not finish in 60.0s -- job=radarr_4K_search elapsed=87.3s -- forcing close` (WARNING)

and the recommended Docker deployment now actually waits long enough for these to
appear before SIGKILL.

Output:

  from `float(os.environ.get("TRIGGARR_SHUTDOWN_DRAIN_TIMEOUT", "60.0"))` clamped

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scheduler in-memory state → log stream | `app.state.search_lock_holder` tuple contains `job_id` (operator-controlled `app_name` + `instance_name`) and a monotonic float — no secrets |
| shutdown signal (SIGTERM, lifespan exit) → in-flight cycles | A long-running cycle holds the lock; shutdown drain waits up to `_SHUTDOWN_DRAIN_TIMEOUT` (default 60s) before forcing close; the holder INFO log fires on entry and the WARNING fires on timeout |
| host process manager (Docker / systemd) → application | The process manager's stop-timeout MUST exceed the in-process drain timeout, otherwise SIGKILL preempts the cleanup. Triggarr documents this requirement in docker-compose.yml (stop_grace_period: 90s) and README.md (--stop-timeout / TimeoutStopSec) |
| env → module constant | `TRIGGARR_SHUTDOWN_DRAIN_TIMEOUT` is read at import time; malformed values fall back to 60.0; values < 1.0 are clamped up to prevent disabling the drain |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-65-08 | Tampering | Holder-set OUTSIDE the lock would allow two jobs to overwrite each other | mitigate | Holder assignment lives INSIDE `async with app.state.search_lock:` (PATTERNS.md invariant); only one writer at a time because the lock guarantees mutual exclusion |
| T-65-09 | Repudiation | Operator cannot tell which instance caused a shutdown timeout | mitigate (closed by this plan) | The new INFO log on entry AND the WARNING on timeout both include `job=` + `elapsed=` — operator can correlate to the specific (app_name, instance_name) pair, even if the process is SIGKILLed before the timeout |
| T-65-10 | Information Disclosure | `time.time()` vs `time.monotonic()` — wall-clock leak | accept | `time.monotonic()` is opaque (no calendar/timezone info); no security-relevant disclosure; chosen for correctness (NTP correction immunity) per RESEARCH Pitfall 3 |
| T-65-11 | Denial of Service | A test monkeypatch of `_SHUTDOWN_DRAIN_TIMEOUT` could be left at 0.1s and leak into production | accept | Monkeypatch is fixture-scoped (pytest tears down on test exit); production startup re-reads the module-level constant; convention is that production code never imports from the test module |
| T-65-14 | Denial of Service | Operator sets `TRIGGARR_SHUTDOWN_DRAIN_TIMEOUT=0` (disables drain → silent data loss on shutdown) | mitigate (Codex finding 3) | Module-level constant clamps to `>= 1.0` so a misconfiguration cannot disable drain entirely; the env-var override test verifies this clamp |
| T-65-15 | Denial of Service | Docker SIGKILLs the process before the in-process drain completes (Codex finding 3) | mitigate | docker-compose.yml declares stop_grace_period: 90s (> 60s default drain); README documents the same requirement for non-compose Docker users and systemd users; the new INFO-on-entry log emits holder context immediately so operator sees what was draining even if SIGKILL races |
