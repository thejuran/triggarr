<objective>
Extend the graceful-shutdown lock-drain timeout from 35s to 60s and replace the
non-actionable single-line warning with a structured warning that names which job
was holding the lock and how long it had been running. Achieve this by extracting
the timeout into a module-level constant (`_SHUTDOWN_DRAIN_TIMEOUT = 60.0`) so tests
can patch it to a sub-second value, tracking the holder identity on
`app.state.search_lock_holder: tuple[str, float] | None`, and reading the holder
inside the existing `except TimeoutError:` branch of `create_lifespan`'s finally block.

Purpose: RES-01. Today's 35s timeout fires the warning `"Shutdown: search cycle did
not finish in 35s — forcing close"` with no indication of which Radarr/Sonarr/Lidarr
instance is stuck. After this plan, the operator sees:
`Shutdown: search cycle did not finish in 60s -- job=radarr_4K_search elapsed=87.3s
-- forcing close` and has actionable information.

Output:
- `triggarr/search/scheduler.py` — module constant `_SHUTDOWN_DRAIN_TIMEOUT = 60.0`;
  `app.state.search_lock_holder: tuple[str, float] | None = None` initialization
  alongside the other `app.state.*` lines in `create_lifespan`; holder set inside
  the `async with app.state.search_lock:` block in `make_search_job`, cleared in a
  `finally` inside the same block; rewritten shutdown TimeoutError branch that reads
  the holder and logs `job` + `elapsed`.
- `tests/test_scheduler.py` — `test_shutdown_timeout_is_60s` asserts the constant
  value; `test_shutdown_timeout_logs_holder_identity` simulates a never-releasing
  lock + patches `_SHUTDOWN_DRAIN_TIMEOUT` to 0.1s and asserts the log message.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scheduler in-memory state → log stream | `app.state.search_lock_holder` tuple contains `job_id` (operator-controlled `app_name` + `instance_name`) and a monotonic float — no secrets |
| shutdown signal (SIGTERM, lifespan exit) → in-flight cycles | A long-running cycle holds the lock; shutdown drain waits up to 60s before forcing close; the new holder log identifies which cycle caused the timeout |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-65-08 | Tampering | Holder-set OUTSIDE the lock would allow two jobs to overwrite each other | mitigate | Holder assignment lives INSIDE `async with app.state.search_lock:` (PATTERNS.md invariant); only one writer at a time because the lock guarantees mutual exclusion |
| T-65-09 | Repudiation | Operator cannot tell which instance caused a shutdown timeout | mitigate (closed by this plan) | The new warning log includes `job=` + `elapsed=` — operator can correlate to the specific (app_name, instance_name) pair |
| T-65-10 | Information Disclosure | `time.time()` vs `time.monotonic()` — wall-clock leak | accept | `time.monotonic()` is opaque (no calendar/timezone info); no security-relevant disclosure; chosen for correctness (NTP correction immunity) per RESEARCH Pitfall 3 |
| T-65-11 | Denial of Service | A test monkeypatch of `_SHUTDOWN_DRAIN_TIMEOUT` could be left at 0.1s and leak into production | accept | Monkeypatch is fixture-scoped (pytest tears down on test exit); production startup re-reads the module-level constant; convention is that production code never imports from the test module |
</threat_model>
