## Summary

This phase has almost no "library choice" research surface — the stack is fixed by prior decisions (Codex CLI, Docker, the existing `tests/codex_review_run.py`/`tests/codex_report_status.py` pair). The real research value is in verifying, hands-on, exactly how the installed tools behave on this machine and this Docker Desktop, because the two reference drafts (DRAFT-85-20, DRAFT-85-21) were written against a planning-time snapshot that must be re-confirmed, not trusted. This session re-ran or directly verified nearly every load-bearing technical claim: the Codex CLI version and flag set, the full `codex features list` output, the Linux arm64 release binary's sha256 (downloaded and re-hashed, matches GitHub's own digest exactly), that binary's flag parity when run inside a disposable container on this Docker Desktop, the exact `docker inspect` shape of a created-but-not-started container (confirming Config.Env has no `HOSTNAME` before start), the Docker-injected runtime environment of a *started* container (confirming `HOSTNAME` and a default `HOME=/` both appear only once the process is actually running — directly explaining B16), and the symlink/FIFO behavior of a Docker Desktop (macOS, virtiofs) bind mount, including that Python's `O_NOFOLLOW` correctly refuses the planted symlink and `O_NONBLOCK` + `fstat(S_ISREG)` correctly detects the planted FIFO (directly verifying B15's prevention mechanism works on this exact host).

The single most consequential finding is on **D-08** (credential refresh): Codex's ChatGPT-login `auth.json` refresh tokens are rotated (single-use) on the OpenAI side, and OpenAI's own CI/CD guidance explicitly warns that an ephemeral runner must write the refreshed file back or the host's copy goes stale — the opposite of D-06's "never copy back." Deleting the container's copy without copying it back does **not** undo a mid-run refresh: if the container's copy of `auth.json` gets refreshed, the host's on-disk refresh token has already been spent server-side, and the *host's own next login* will fail with `refresh_token_reused`, forcing a manual re-login. D-06 already accepts this as residual risk, but the design needs a concrete mitigation, not just detection: force (or confirm) a fresh host-side refresh immediately before copying (so the ~8–10 day staleness window can't be crossed during a ≤30-minute review run), and hash-compare the copy before/after as the detection+evidence mechanism D-08 asks for.

The second most consequential finding is a **planning gap in the reference drafts**: neither DRAFT-85-20 nor DRAFT-85-21 lists `.github/scripts/acceptance-readiness.cjs` or `.github/scripts/codex-fallback.cjs` in `files_modified`, but both scripts currently hard-code "an untrusted head's Codex result is always refused; the fallback is the only path to acceptance." Once this phase ships a genuinely COMPLETE inspection-only review, those two scripts (plus their tests, plus `tests/test_review_checkpoint_record.py`'s explicit "`.ci-evidence.json`/`.grader-provenance.json`/`.boundary.json` must not appear yet" guard, plus `tests/test_acceptance_docs.py`) will still force every untrusted head through the manual fallback unless they are updated in this phase. Without this, the phase's own code would work but the owner-acceptance path would never actually use it.

**Primary recommendation:** Build Task 1 (checker inspection-only mode + prompt) and Task 2 (runner inspection-only path with fail-closed boundary gate, no container yet) essentially as DRAFT-85-20 specifies — it was already fully re-planned and detailed, and nothing in this research contradicts it. Build Task "85-21-equivalent" (image + container launch + deterministic verification) using the version-matched, digest-verified Linux `aarch64-unknown-linux-musl` Codex binary confirmed below, and add the CONTAINER_BASE_ENV vs. CANARY_EXPECTED_ENV split this research found necessary (B16 is a canary-check problem, not a `docker inspect` problem). Add a new, explicit task (not in either draft) to update `acceptance-readiness.cjs`, `codex-fallback.cjs`, `docs/review-checkpoint-record.md`, `docs/codex-adversarial-review-contract.md`'s Invocation section, `tests/test_review_checkpoint_record.py`, and `tests/test_acceptance_docs.py` so a COMPLETE inspection-only review is actually recognized by the acceptance gate. Structure the plan's waves around the pre-merge/post-merge split D-01..D-03 require (see Architecture Patterns).

### Pattern 1: Create-before-start deterministic inspection
**What:** `docker create` (never `docker run`) to get a container ID without executing anything, `docker inspect` that ID, compare the JSON against an expected shape, and only `docker start` the *same* container ID if the comparison passed.
**When to use:** Any time a container's configuration itself is the security boundary (not just what runs inside it) — exactly B04-R3's requirement that isolation be checked deterministically, not behaviorally.
**Verified example (this session, read-only python:3.13-slim, no credentials):**
```bash
# Source: direct execution against Docker Desktop 29.4.3 on this machine, 2026-10-28
CID=$(docker create -i --read-only \
  --tmpfs /work:rw,size=64m,mode=0700,uid=10001,gid=10001 \
  --tmpfs /tmp:rw,size=64m,mode=1777 \
  --user 10001:10001 --cap-drop ALL --security-opt no-new-privileges \
  --pids-limit 256 --memory 2g --network bridge \
  --mount type=bind,src=/tmp/codex-home-test,dst=/codex-home \
  --mount type=bind,src=/tmp/out-test,dst=/out \
  -e CODEX_HOME=/codex-home -w /work \
  python:3.13-slim sleep 300)
docker inspect "$CID"   # inspected BEFORE any docker start
```
Verified result: `Config.Env` at this point is **exactly** `['CODEX_HOME=/codex-home', 'PATH=...', 'LANG=...', <base-image's own baked-in ENV vars>]` — no `HOSTNAME`. `HostConfig.ReadonlyRootfs: true`, `CapDrop: ["ALL"]`, `CapAdd: null`, `SecurityOpt: ["no-new-privileges"]`, `Privileged: false`, `NetworkMode: "bridge"`, `PidMode: ""`, `IpcMode: "private"`, `Devices: []`, `HostConfig.Mounts` lists exactly the two bind mounts with their host sources.

### Pattern 2: Two separate "expected environment" sets (resolves B16)
**What:** The static `docker inspect` check (`verify_container_config`) and the live-process canary check (`parse_canary_check`) see **different** environments, so they need **different** expected-name sets.
**When to use:** Always, for this design. Conflating them is exactly what B16 flagged.
**Verified distinction (this session):**
```bash
# Source: direct execution, python:3.13-slim, verified this session
docker run --rm --read-only --tmpfs /tmp:rw,size=16m --user 10001:10001 \
  -e CODEX_HOME=/codex-home python:3.13-slim env
# -> PATH=... HOSTNAME=f5008c8e5f3b CODEX_HOME=/codex-home LANG=... <image ENV...> HOME=/
```
`HOSTNAME` (Docker always injects a random container-id-derived hostname once a container *starts*, never present at `create`-time inspect) and a default `HOME=/` (Docker/runc defaults HOME to `/` when the numeric `--user` has no matching `/etc/passwd` entry and the image sets no `ENV HOME`) **both appear only in the live runtime environment**, never in the pre-start `docker inspect` Config.Env. Recommendation: `CONTAINER_BASE_ENV` (for `verify_container_config`) stays `{PATH, HOME, LANG, CODEX_HOME}` plus forwarded names (correct as drafted, since the review image should explicitly `ENV HOME=/home/review` to avoid the `/` default — already in DRAFT-85-21's Dockerfile plan). A **separate** `CANARY_EXPECTED_ENV` for `parse_canary_check` must additionally allow `HOSTNAME` (always present, unavoidable, carries no secret — just a random container ID) and, if the canary script itself is invoked via `sh -c` (it is, per `container_check_argv`), `PWD` (shell-set, not Docker-set). Do **not** widen `CONTAINER_BASE_ENV` to include these — that would reintroduce the "broad allowlist" B16 explicitly rejected; keep the two checks and their two expected-sets separate.

### Pattern 3: Stop-then-safe-read of container output (verifies B15 works on this host)
**What:** After `docker rm -f` (or at minimum after confirming the container has exited), read the output file with `O_NOFOLLOW` (refuses a symlink) then `fstat` + `S_ISREG` (refuses a FIFO that *did* open) with a size bound.
**Verified end-to-end (this session, Docker Desktop macOS/virtiofs bind mount):**
```python
# Source: direct execution against this Docker Desktop (4.73.0, virtiofs), 2026-10-28.
# A container ran: ln -s /etc/passwd /out/last.json ; mkfifo /out/fifo.json
import os, stat
fd = os.open("/tmp/out-test2/last.json", os.O_RDONLY | os.O_NOFOLLOW | os.O_NONBLOCK)
# -> OSError: [Errno 62] Too many levels of symbolic links   (ELOOP -- symlink correctly refused)

fd = os.open("/tmp/out-test2/fifo.json", os.O_RDONLY | os.O_NOFOLLOW | os.O_NONBLOCK)
# -> succeeds (non-blocking open on a FIFO with no writer is allowed)
stat.S_ISREG(os.fstat(fd).st_mode)   # -> False
stat.S_ISFIFO(os.fstat(fd).st_mode)  # -> True   (caller must check this and refuse/close)
```
**Confirmed:** a container really can create a genuine host-visible symlink or FIFO inside a bind-mounted directory on this exact Docker Desktop setup (virtiofs does not silently convert or block them) — the B15 threat is real on this host, not theoretical — and the documented mitigation (`O_NOFOLLOW` pre-open, `O_NONBLOCK` + `fstat(S_ISREG)` post-open) correctly defeats both planted artifacts. A regular file's `fstat` after the same open sequence correctly reports `S_ISREG: True`, so the positive case is not broken by this check.

### Pattern 4: Pin-and-verify an externally fetched binary (existing repo convention to copy exactly)
**What:** `ENV <NAME>_VERSION`, `ENV <NAME>_SHA256`, `curl -fsSLO <url>`, `echo "$SHA256  $file" | sha256sum -c -`, then extract. This repo already does this twice in `.github/workflows/ci.yml` (`ACTIONLINT_VERSION`/`ACTIONLINT_SHA256` and `TRIVY_VERSION`/`TRIVY_SHA256`, lines ~214-230 and ~395-413).
**Example for this phase (verified digest):**
```dockerfile
# Source: this repo's .github/workflows/ci.yml actionlint/Trivy pattern, mirrored here;
# digest independently re-verified this session (shasum -a 256 matched GitHub's own digest)
ARG CODEX_VERSION=0.153.4
ARG CODEX_SHA256_ARM64=5cda6182bd94c3a30f2eb63a495489ebf7f691fddb14d70f48c6c1a5071b6cde
RUN curl -fsSLO "https://github.com/openai/codex/releases/download/rust-v${CODEX_VERSION}/codex-aarch64-unknown-linux-musl.tar.gz" \
    && echo "${CODEX_SHA256_ARM64}  codex-aarch64-unknown-linux-musl.tar.gz" | sha256sum -c - \
    && tar -xzf codex-aarch64-unknown-linux-musl.tar.gz \
    && mv codex-aarch64-unknown-linux-musl /usr/local/bin/codex \
    && chmod +x /usr/local/bin/codex
```

### Anti-Patterns to Avoid

- **Mounting the host `~/.codex` directory (even read-only) into the container:** It is 737 MB of operator state on this machine (agents, memories, skills, session history, plugins) — enormously more than a credential, and read-only mounting the *whole* directory does not stop Codex's own writes to `CODEX_HOME` (session/log/sqlite state) from failing confusingly at best, or (per community reports in Common Pitfalls) from racing the host's own live Codex process's SQLite WAL files at worst. D-06 already specifies copying only `auth.json`; this research confirms that's the right call, not just the simpler one.
- **Treating `docker inspect`'s `Config.Env` and a live canary `env` dump as the same list to validate against the same expected set.** They are genuinely different (Pattern 2) — conflating them either breaks the static check (by widening it to admit `HOSTNAME`) or breaks the canary check (by rejecting the `HOSTNAME`/`PWD` Docker and the shell legitimately add).
- **Assuming the npm-wrapped macOS `codex` binary and the raw Linux release tarball binary have different flags.** Verified this session they are flag-identical for `0.153.4` (ran the actual Linux `aarch64-unknown-linux-musl` binary inside a disposable container and diffed its `--help` output against the host's).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Verifying a container's security configuration | A custom "ask Codex if it used a tool" self-report as the isolation proof | `docker create` + `docker inspect` + a field-by-field comparison (already the DRAFT-85-21 design) | A model can simply be wrong or silent about using a tool; a `docker inspect` field is a fact about the kernel/runtime configuration, not a claim |
| Detecting whether the copied credential changed during a run | Parsing/diffing the JWT contents of `auth.json` | A plain `sha256sum` of the whole file, computed before copy-in and after copy-out (before deletion) | Simpler, doesn't require decoding JWTs or touching secret values at all, and answers exactly the yes/no question D-08 needs |
| Binary integrity verification | A hand-rolled checksum database | This repo's own existing `ACTIONLINT_SHA256`/`TRIVY_SHA256` pattern in `ci.yml`, applied to `CODEX_SHA256_ARM64` | Already an established, reviewed convention in this exact repo; no need to invent a second way to pin external binaries |
| Deciding whether a PR's Codex result should still require the manual fallback | A new ad hoc check in the plan's own code | Updating the **existing** `acceptance-readiness.cjs`/`codex-fallback.cjs` logic that already encodes this decision (currently hard-coded to always require the fallback for `headTrust === 'untrusted'`) | The decision logic already exists and is already tested; it is simply stale once inspection-only mode ships, and must be updated in place, not duplicated |

**Key insight:** every piece of this design already has a close analog somewhere else in the repo (checksum-pinning in CI, fail-closed status stubs, atomic-write-then-rename, the trusted-main cross-grade pattern from Phase 85-13). The research task here was confirming those analogs transfer correctly to a new context (a container boundary), not inventing new mechanisms.

## Common Pitfalls

### Pitfall 1: A mid-run credential refresh breaks the host's login, even with D-06 followed perfectly
**What goes wrong:** The container's copy of `auth.json` gets refreshed by Codex during the run (because the access token had already gone stale before the run started); the refresh **rotates the single-use refresh token on OpenAI's server**, so the host's on-disk (unchanged) copy of that same refresh token is now spent. The *next* time the host's own Codex session tries to refresh (potentially days later, unrelated to this phase), it fails with `refresh_token_reused` and the owner has to `codex login` again.
**Why it happens:** [CITED: `learn.chatgpt.com/docs/auth/ci-cd-auth`, fetched 2026-10-28] Codex refreshes automatically "if `last_refresh` is older than about 8 days," and [MEDIUM confidence, multiple third-party GitHub issues cross-referenced, e.g. `pydantic-ai#10266`, `assistant-runtime#173`, `ralphex#411`] the refresh token is rotated/single-use — a second party (or a second copy) that tries to use the *old* refresh token after another copy already spent it gets `refresh_token_reused`. D-06's "never copy back" prevents the container's *new* tokens from overwriting the host file, but does nothing to prevent the host's *old* refresh token from having already been spent by the container.
**How to avoid:** Not fully preventable without copying back (which D-06 forbids) or using an API key (which D-06 declines) — but the exposure window is small and manageable: (1) before copying `auth.json` into the per-run temp dir, do a cheap host-side preflight (e.g. `codex login status`, confirmed this session to **not** rewrite `auth.json`'s mtime when the session isn't stale) to confirm the credential isn't already past its staleness window; if it is, require a host-side `codex` command to run first (outside the container) so the copy starts freshly refreshed, since the review itself runs in ≤30 minutes (`CODEX_TIMEOUT_SECONDS = 1800` in the existing runner) — vastly shorter than the ~8–10 day staleness window, so a freshly-refreshed copy is very unlikely to need a second refresh mid-run. (2) Hash the copy immediately before container start and again immediately after container exit (before deletion) — this is exactly the "detect it and stop" D-08 asks for, and should be recorded in the boundary/run evidence either way. (3) The D-08 live-evidence requirement ("showing that the host login still works after a run") should use a check that would actually surface server-side revocation (reading `last_refresh`/`has_refresh_token` structurally is necessary but not sufficient — only an actual authenticated call proves the token still works; this is an **open question** for the executor, not resolved by this research).
**Warning signs:** `auth.json`'s sha256 (or just its `last_refresh` field) differs between pre-copy and post-run; the next *unrelated* host-side Codex session demands `codex login` again.

### Pitfall 3: The acceptance gate does not know about inspection-only mode and will keep demanding the manual fallback
**What goes wrong:** `.github/scripts/acceptance-readiness.cjs` line ~76-77 and ~108-109, and `.github/scripts/codex-fallback.cjs` line ~301-302 and ~313-319, all hard-code the assumption "an untrusted head's Codex evidence can never legitimately claim complete; it is always refused until Phase 85.1 and always needs the owner-approved fallback." Specifically: `acceptance-readiness.cjs`'s `claimsComplete` check only recognizes `meta.review_mode === 'trusted-local-tests'`, and separately, **any** `headTrust === 'untrusted'` branch unconditionally requires either the hard-coded `'untrusted-refused'` review mode or a validated fallback record — there is no branch for "untrusted head, `review_mode: 'inspection-only-ci-evidence'`, genuinely complete." If this phase ships the container+runner changes but not this file, a real COMPLETE inspection-only review would still be rejected by the acceptance gate and every bot/fork PR would still need the manual fallback, defeating D-07's point.
**Why it happens:** Neither DRAFT-85-20 nor DRAFT-85-21's `files_modified` headers list `acceptance-readiness.cjs` or `codex-fallback.cjs` — they were written focused on the review/isolation machinery itself, not the downstream acceptance consumer.
**How to avoid:** Add an explicit task (or fold into the final task of the last wave) that updates both scripts to recognize a `review_mode` of `"inspection-only-ci-evidence"` (or whatever the final name is) as a legitimate complete-for-untrusted-head path, update their test files, and update `docs/review-checkpoint-record.md`'s "D-07 is delivered for untrusted heads by Phase 85.1" line and `docs/codex-adversarial-review-contract.md`'s Invocation section (currently says "Until Phase 85.1 delivers the isolated review, untrusted heads... get an INCOMPLETE Codex result").
**Warning signs:** `grep -rn "Phase 85\.1\|untrusted-refused" .github/scripts/*.cjs tests/*.py docs/*.md` (run this session; found 13 files outside the 85/85.1 phase directories that reference this wording — see list below) still returns hits after the phase is "done."

### Pitfall 4: Two drift-guard tests will actively fail (by design) until updated
**What goes wrong:** `tests/test_review_checkpoint_record.py::test_raw_output_paths_include_new_outputs` currently asserts, verbatim, `for not_yet in (".ci-evidence.json", ".grader-provenance.json", ".boundary.json"): assert not_yet not in text, f"{not_yet} is Phase 85.1 work and must not appear yet"`. Once this phase's docs legitimately add those output-file names to `docs/review-checkpoint-record.md`, this test will fail — correctly, since it's a deliberate "not yet" guard, not a bug. Likewise `tests/test_acceptance_docs.py` asserts the exact "Until Phase 85.1 delivers..."/`"untrusted-refused"` substrings exist in the contract doc.
**Why it happens:** These are exactly the kind of forward-looking negative guards GSD/TDD encourages, written during Phase 85 to prevent *accidentally* describing unbuilt work as built. They are supposed to need updating now.
**How to avoid:** Treat updating these two test files as an explicit, expected part of this phase's scope (not a regression to investigate) — flip the "not yet" assertions once the corresponding doc changes land, in the same commit as the doc change.
**Warning signs:** `uv run pytest tests/test_review_checkpoint_record.py tests/test_acceptance_docs.py -x -q` failing after a docs-only commit in this phase is **expected**, not a bug — but it must be fixed in the same phase, not left broken.

### Pitfall 5: Digest-pinning the review image's base is a new convention in this repo, not an existing one
**What goes wrong:** DRAFT-85-21's read-first list says to check "Dockerfile at the repository root (how this repo pins base images by digest)" — but [VERIFIED: `grep -rn "@sha256" --include="*.yml" --include="Dockerfile*" .` across the whole repo, 2026-10-28] returned **zero** matches. The root `Dockerfile` uses `FROM python:3.13-slim` (tag only, no digest) in all three of its stages. GitHub Actions *are* pinned by full SHA (confirmed, e.g. `actions/checkout@3d3c42e5aac...`), but Docker `FROM` images are not, anywhere in this repo today.
**Why it happens:** The draft's phrasing assumed a convention that turned out not to exist; likely conflating the Actions-pinning convention with Docker-image pinning.
**How to avoid:** Decide explicitly (don't assume): digest-pin the new review image's base anyway (recommended, since this is specifically a security-isolation image and digest-pinning is strictly stronger), and say so plainly in the Dockerfile's header comment as a **deliberately new, narrower convention** for this one security-sensitive image — don't claim it "matches existing repo practice."
**Warning signs:** A reviewer or future maintainer asking "why does only this one Dockerfile pin by digest?" — answer that question in the file itself.

### Pitfall 6: The review-machinery drift guard (`tests/test_review_machinery_lists.py`, Phase 85 D-17) doesn't know about the new `docker/codex-review/` directory
**What goes wrong:** This existing test cross-checks three hand-kept lists (the classification policy's sensitive row, `AUDITED_INPUTS` in `codex_review_run.py`, and the acceptance checklist's Codex line) for agreement. The new `docker/codex-review/Dockerfile` is conceptually "review machinery" (it defines the isolation boundary) but is not mentioned in `docs/review-classification-policy.md`'s sensitive row's file list, and doesn't obviously belong in `AUDITED_INPUTS` either (that list is specifically "files that decide what Codex is told and how its report is judged," which containment arguably is not).
**Why it happens:** The policy's sensitive-file list and the drift guard predate this phase's new directory.
**How to avoid:** Explicitly decide (and record the rationale) whether `docker/codex-review/**` joins `review-classification-policy.md`'s sensitive row (recommended — it is unambiguously part of "the review machinery... `tests/codex_review_run.py`, `tests/codex_report_status.py`" the policy already lists) and whether the three-list drift guard should grow a fourth list or stay scoped to its original three. This is an **open question** for the planner, not resolved here.
**Warning signs:** A future PR touches `docker/codex-review/Dockerfile` and gets classified `ordinary-docs` or `code` instead of `sensitive`, skipping the risk assessment this kind of change should get.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | Codex ChatGPT-login OAuth token handling (D-06/D-08) — standard practice is "use the dedicated non-interactive credential type for automation" (OpenAI's own API-key recommendation); this phase deliberately uses the interactive-login credential instead, per locked owner decision, with the mitigations in Common Pitfalls #1 |
| V3 Session Management | yes | The container's lifetime *is* the credential-copy's session; `docker rm -f` + temp-dir deletion is the session-termination control |
| V4 Access Control | yes | `--cap-drop ALL`, `--security-opt no-new-privileges`, non-root numeric UID, read-only root filesystem — standard container least-privilege controls, all verified reproducible on this Docker Desktop this session |
| V5 Input Validation | yes | The untrusted head's content is validated only as *inert text* (size-bounded, binary-detected, never executed) — this is the core of the whole design, not a bolt-on |
| V6 Cryptography | yes | sha256 integrity verification of the Codex binary and (implicitly) the base image digest — never hand-rolled, uses the OS's `sha256sum`/`shasum` and Docker's own digest mechanism |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Prompt injection in untrusted diff/file content attempting to make the model invoke a tool | Tampering / Elevation of privilege | `--disable` every tool-capable feature (defense in depth) + deterministic container isolation (the actual guarantee) + post-run event-type audit (`audit_event_types`) that fails closed on *any* unexpected item type, regardless of what the model's own report claims |
| Symlink/FIFO planted in a bind-mounted output directory to read host files or hang the reader | Information disclosure / Denial of service | Stop-then-read with `O_NOFOLLOW` + `O_NONBLOCK` + `fstat(S_ISREG)` + size bound — verified working on this exact host this session (Architecture Patterns Pattern 3) |
| Credential exfiltration via open network egress from inside the container | Information disclosure | Not mitigated in this phase by design (D-04, locked) — explicitly documented as accepted residual risk (D-07); the only secret present is the Codex credential copy, deleted after every run and never copied back (D-06) |
| Fork-controlled base commit supplying the "grader" that judges its own PR | Elevation of privilege / Tampering | `establish_trusted_main()` — grader is always materialized from a freshly-fetched, ancestor-checked `origin/main`, never from `--base` (B13, already specified in DRAFT-85-20 and unchanged by this research) |
| Supply-chain tampering of the Codex binary or base image baked into the review image | Tampering | sha256 pin verified against GitHub's own reported digest (done this session); base image resolved via `docker buildx imagetools inspect` to get the exact current digest before pinning |
