**F001 fix, how it was checked:**
- **The reader:** `_run_bounded_output` reads at most `max+1` bytes, then kills the process and reaps it. `_git_bounded` checks the length before the exit code.
- **The budget:** `build_inspection_input` keeps a running byte budget.
  - The diffs are read with a bound of `budget - used`. The path lists are bounded by the whole budget.
  - `cat-file -s` runs before any blob read. A blob larger than the remaining budget is never fetched.
  - The budget is never negative at a read, because `_add` stops at `used > budget`.
  - A decode that inflates invalid UTF-8 can only push the input over the budget, so it fails closed.
- **When the input is oversize,** nothing is rendered, and the `.prompt.txt` file is a one-line note.

### Fixer's judgement calls

- **"CI ready" from another app is ignored, not refused: agree.**
  - **Why it is safe:** such a check run can never satisfy the rule, because only `github-actions` check runs are candidates. If it were the only success, the result is still "no successful CI ready".
  - **Why not refuse instead:** refusing would let any installed app block every PR just by posting a check with that name.
  - **Both sides agree:** Python (`codex_review_run.py:887-892`) and JS (`acceptance-readiness.cjs:184-185`) filter the same way.
- **The fork check runs after the CI check: agree.**
  - **Why the order is safe:** a fork whose CI did not pass, or whose added workflow posts its own "CI ready", is refused before the reservation (exit 2). The acceptance gate's CI-ready item blocks that head anyway, so a fallback could not rescue it.
  - **What the fork check covers:** only the case the ruling is about, a passing CI that may not be independent.

## Warnings

### WR-01: The fork rule misses CI gate files under `.github/` that the unchanged `ci.yml` executes from the head

**File:** `tests/codex_review_run.py:1088` (`CI_DEFINITION_PATHSPECS`), `docs/codex-adversarial-review-contract.md:90`

**Issue:** The ruling's rationale is this: under `pull_request`, a fork's own files decide what its CI checks, so its "CI ready" is not independent evidence. The pathspec only covers workflow and action definitions.

**How `ci.yml` uses head-supplied gates:** under `pull_request`, `ci.yml` runs head-supplied scripts and data from `.github/` as the pass/fail decision for whole required jobs:
- `os-scan` job (`ci.yml:421`): `node .github/scripts/os-scan-gate.cjs --exceptions .github/os-scan-exceptions.json`.
- `dependencies` job (`ci.yml:159-160`): `.github/scripts/image_lock_consistency.py`.
- `test` job (`ci.yml:76`): `.github/scripts/coverage-provenance.cjs`. The `test` job also runs the `node --test .github/scripts/*.test.cjs` glob (`ci.yml:42`).

**The gap:** a fork PR that leaves `ci.yml` alone can do either of these:
- add every OS CVE to `.github/os-scan-exceptions.json`;
- make `os-scan-gate.cjs` exit 0.

Either way it gets a green `os-scan` and therefore a green "CI ready" from a genuine `ci.yml` run. The runner then does not route the PR to the fallback, and `_ci_evidence_text` tells Codex the CI passed for this head.

**Why this deserves a stronger rule than ordinary test changes:**
- **Ordinary edits:** changes to `tests/` are ordinary code under review.
- **Gate files:** these files are the CI gates themselves, the same class of change as editing `ci.yml`. The vulnerability gate is exactly where a malicious contribution would want to hide.

**Fix:** Widen the pathspec to the whole directory. It is just as cheap, still fails safe, and same-repository and Dependabot PRs are still exempt.

```python
CI_DEFINITION_PATHSPECS = (".github",)
```

Then:
- Update the contract paragraph to "any file under `.github/`".
- Add parametrized test cases for `.github/os-scan-exceptions.json` and `.github/scripts/os-scan-gate.cjs`.

If the owner prefers the narrow rule, record that the narrow rule was deliberate in the contract, so the gap is a known, accepted gap rather than an unnoticed one.
