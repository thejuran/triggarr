## Assumption Drift (advisory)

**1. Base image digest changed between RESEARCH and this plan's execution**
- **Planned:** 85.1-RESEARCH.md and 85.1-PATTERNS.md both cite the `debian:bookworm-slim` `linux/arm64` manifest digest as `sha256:a3bba7dc7dbcc1f37c2856c51fc9a7fac96608f50cb87b1b4e4d8b8c85ae988e` (verified 2026-10-28 during research).
- **Actual:** Re-running `docker buildx imagetools inspect debian:bookworm-slim` at execution time (also 2026-10-28, later the same day) returned a *different* `linux/arm64` manifest digest: `sha256:7ccb8b5b60c7654f5b795d94ee7d751cd0811500803f0b09cefcd555e755a55a`. Cross-checking the raw manifest-list JSON confirms this is genuinely the `arm64` entry (`"architecture": "arm64", "variant": "v8"`), and separately that the RESEARCH-cited digest `a3bba7dc...` is actually the `linux/amd64` entry in the manifest list retrieved at execution time — either the tag was rebuilt between research and execution, or the research session's platform label was transposed. Used the freshly-resolved `arm64` digest (`7ccb8b5b...`) in the Dockerfile, per the plan's explicit "re-resolve the base digest immediately before writing it" instruction.
- **Why:** `debian:bookworm-slim` is a floating tag; Docker Hub's official image can be rebuilt at any time, and research and execution happened as two separate `docker buildx imagetools inspect` calls hours apart on the same day.
- **Cost if wrong:** Low. The plan anticipated exactly this risk and instructed re-resolution at write time; the only way this could matter is if the pin becomes stale again before Plan 85.1-10 actually builds the image, in which case `docker build` will simply fail closed on a digest mismatch (Docker refuses to pull a tag whose resolved digest doesn't match a pinned `@sha256:...` reference) rather than silently using the wrong base.
