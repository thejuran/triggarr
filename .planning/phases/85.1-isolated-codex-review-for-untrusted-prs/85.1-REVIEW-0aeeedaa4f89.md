## Warnings

### WR-01: The Dockerfile binding hashes the working-tree file, not the committed one

**File:** `tests/codex_review_run.py:1442-1452`, `1913-1919`, `86-91`
**Issue:**
- **What is hashed:** `review_image_dockerfile_sha256()` hashes `HARNESS_ROOT / "docker/codex-review/Dockerfile"` straight from the working tree.
- **Why nothing else covers it:** that file is not in `AUDITED_INPUTS`. So `establish_trusted_main()`'s "audited inputs committed and clean" check and the post-run re-audit both ignore it.
- **The resulting gap:** an operator can edit the Dockerfile without committing, rebuild with the documented `shasum` command, and the gate accepts the image. The record then shows a `dockerfile_sha256` that matches no committed file.

This is WR-09's original failure (an image that is not main's passes the gate), moved from "another branch" to "an uncommitted edit". The refusal message and the docstring both say "committed Dockerfile", which is not what the code checks. The contract says "the checkout's own", which is accurate but weaker than the stated intent (the image should be main's).

**Fix:** Bind the hash to committed content. Either:
- add `docker/codex-review/Dockerfile` to `AUDITED_INPUTS`, which brings in the dirty check, the post-run re-audit and the meta hash for free. Update the drift and list tests (`test_review_machinery_lists.py`). Or:
- hash the committed blob directly, and refuse when the working tree differs:

```python
def review_image_dockerfile_sha256(command_runner: CommandRunner) -> str:
    blob = _git_bytes(["git", "show", f"HEAD:{REVIEW_IMAGE_DOCKERFILE_RELPATH}"], command_runner)
    if blob != REVIEW_IMAGE_DOCKERFILE.read_bytes():
        raise RunnerError(f"{REVIEW_IMAGE_DOCKERFILE_RELPATH} has uncommitted changes")
    return hashlib.sha256(blob).hexdigest()
```

### WR-02: The single-check-suite CI rule refuses a legitimate close/reopen

**File:** `tests/codex_review_run.py:798-815`
**Issue:**
- **What the rule assumes:** the refusal treats "more than one check suite posted CI ready" as "more than one workflow posted it". That is not the same thing.
- **Re-runs are fine:** re-running a run's jobs keeps the same check suite, which the fix handles.
- **A reopen is not:** every new *workflow run* for the same head gets its own check suite. `ci.yml` runs on `pull_request` with the default activity types (`opened`, `synchronize`, `reopened`). Closing and reopening a PR, a common way to re-trigger CI and something `@dependabot reopen` also does, starts a second `ci.yml` run for the same head SHA.

That gives two `github-actions` CI-ready runs in two check suites, so `ci_evidence()` refuses with "more than one workflow posted a 'CI ready' check run". The PR can then never get an inspection-only review at that head. It fails closed, but it pushes the PR to the fallback, and the message wrongly suggests a hostile workflow. Existing tests cover only "a re-run in the same suite" and "another app", not this case.
**Fix:** Identify the workflow, not the check suite. For each CI-ready run, look up its workflow run (`gh api repos/{o}/{r}/actions/runs?head_sha=<head>` → `check_suite_id`, `path`) and keep only runs whose `path == ".github/workflows/ci.yml"`. Refuse if any `github-actions` CI-ready run comes from a different workflow path. Among the remaining runs, the latest still wins. Also record `app.slug` and the workflow path in `.ci-evidence.json` (IN-05). Add a regression test with two `ci.yml` suites (reopen) that is accepted, and a test where a second workflow path is refused.

### WR-03: The acceptance gate still takes "CI ready" by name from any app, the vector WR-03 closed in the runner

**File:** `.github/scripts/acceptance-readiness.cjs:162-177`
**Issue:**
- **How the gate picks the check:** `ciReadyItem()` → `latestCheck(checks, head, 'CI ready')` takes the highest-id check run with that name from **any** app and **any** workflow.
- **Why it matters more now:** under D-12 this script now accepts an untrusted head when its inspection-only Codex result is complete.
- **The gap:** a head that adds its own workflow with a passing job named `CI ready`, or any app posting a check with that name, can make the gate show CI ready = ok when the real `ci.yml` CI failed. The runner refuses that exact case after the WR-03 fix. So the two acceptors now disagree on what counts as CI evidence, and the weaker rule sits on the acceptance path that authorizes merge.

The fix report called this "outside this finding's file", but the file is in this phase's scope, and the inconsistency is new in this round.
**Fix:** Apply the same rule as the runner, in one place. Have the check-run read include `app` and `check_suite` (or, after WR-02, the workflow path). Count only `app.slug === 'github-actions'` runs from `ci.yml`, and block when CI-ready runs come from a different workflow. Add parity rows to `codex-completeness-parity.test.cjs`, or a JS/Python CI-evidence parity test.

### SA-03: For a fork PR, the CI evidence comes from the fork's own `ci.yml`

**Where:** `tests/codex_review_run.py:771-830` (`ci_evidence`), `.github/workflows/ci.yml:3-7`
**Why excluded:** Whether fork heads are eligible at all is a product and scope decision. The code cannot make the evidence independent: under `pull_request`, GitHub runs the workflow file from the PR's merge ref.
**Effect if left as is:** A fork PR that edits `ci.yml` (for example, changing the `ci-ready` job to always pass) produces a `github-actions` "CI ready" success in one check suite. Both the runner and the acceptance gate accept it. The inspection prompt then tells Codex "CI passed for this head". Fork workflows need owner approval to run on first contribution, which limits exposure but is not enforced by this tooling.
**Needs:** A ruling. Options:
- (a) Treat a head that changes anything under `.github/workflows/` as not having independent CI evidence (INCOMPLETE → fallback). This is cheap: the changed-path list is already computed.
- (b) Accept the risk and record it in the contract.
- (c) Defer, noting that no fork PR is expected soon.
