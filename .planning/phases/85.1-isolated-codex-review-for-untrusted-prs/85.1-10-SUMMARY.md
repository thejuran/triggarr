## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Host-exposure pre-check flagged 24 fixed non-path literals as host-path exposure**
- **Found during:** Task 2, live run 1
- **Issue:** `host_exposure_problems()` called `os.path.realpath()` on every pre-boundary canary argv token unconditionally, including fixed non-path literals (`ALL`, `bridge`, `256`, `no-new-privileges`, `docker`, `create`). `realpath` resolves a relative string against the process's cwd (the repository root, since the runner is invoked from there), so every one of those literals resolved underneath `REPO_ROOT` and was wrongly flagged as a host-path exposure — 24 false positives that always failed `--verify-boundary` when run for real. Unit test fixtures never caught this because they used a fake `repo_root` distinct from the test process's actual `cwd`.
- **Fix:** `host_exposure_problems()` now only resolves argv tokens that look like absolute paths before calling `realpath()` on them; the host-exposure check also now runs before `prepare_codex_home()` stages the sign-in copy, so a failed pre-check never leaves credential material staged even briefly.
- **Cost if wrong:** If this fix were itself wrong (e.g. missed a real path-like token), the live `--verify-boundary` check would either still false-positive (safe failure mode, caught immediately on re-run) or, worse, fail to flag a real host-path exposure that a non-path-shaped string happened to carry — mitigated by the check remaining fail-closed (any flagged reason still blocks verified) and by the regression test added for this exact cwd scenario.
- **Files modified:** `tests/codex_review_run.py`, `tests/test_codex_review_container.py`
- **Verification:** Live run 2's Step 3 returned `verified` with zero reasons on the same host, same working directory, same commands — directly confirming the fix. Full suite also green (3022 passed, 1 skipped; this session's run).
- **Committed in:** `7d6dbc0` (test, RED), `503a208` (fix, GREEN), `fbbb802` (fix — staging-order correction)

**2. [Rule 1 - Bug] Review image's final stage never carried a CA certificate bundle, breaking TLS to the Codex model backend**
- **Found during:** Task 2, live run 2
- **Issue:** `docker/codex-review/Dockerfile`'s final (review) stage never carried a CA certificate bundle — only the discarded `fetch` stage installed `ca-certificates`. Codex inside the container could not validate the TLS certificate for `wss://chatgpt.com/backend-api/codex/responses` (`invalid peer certificate: UnknownIssuer`), never reached the model backend, and the run hung to its 1800s timeout, producing `error`-typed events that the probe correctly flagged (though the message, at the time, generically said "tool use").
- **Fix:** The final stage now copies the CA bundle forward from the fetch stage instead of discarding it, resolving the TLS handshake failure without adding a fresh `apt-get` layer to the shipped image.
- **Cost if wrong:** If the CA bundle were stale or mismatched, the container would still fail closed (TLS error, no model reached, probe downgrades) rather than silently succeeding with an insecure connection — the failure mode stays safe either way. Confirmed correct by run 3's clean TLS handshake (`codex exit code: 0`, no certificate errors in stderr).
- **Files modified:** `docker/codex-review/Dockerfile`, `tests/test_codex_review_image.py`, `tests/test_codex_review_container.py`
- **Verification:** Live run 3's Step 4 captured stderr contained no `UnknownIssuer`, no websocket connection failures, and no timeout — `codex exit code: 0` confirmed Codex reached the backend successfully.
- **Committed in:** `cdc04eb` (test, RED), `c5e0859` (fix, GREEN)

**3. [Rule 1 - Bug] Probe event labelling called every out-of-allowlist item type "tool use", even non-tool types like a connectivity error**
- **Found during:** Task 2, live run 2
- **Issue:** `_probe_tool_use_reasons()` labelled every item type outside `ALLOWED_ITEM_TYPES` as `"probe used a tool: <type>"`, including the `error` type produced by the TLS/connectivity failure above — a connectivity error is not a tool invocation, so the message was misleading even though the fail-closed verdict (`unverified`) was the correct outcome either way.
- **Fix:** The labelling now distinguishes a known-tool item type from any other type outside the allowlist, so the recorded reason states what was actually observed (`"probe produced an unexpected event: error"`) instead of guessing "tool use" for an event that might be a connectivity failure, a blocked-tool error, or something else entirely.
- **Cost if wrong:** Low — this is a reporting/labelling fix only; it does not change the pass/fail verdict (any out-of-allowlist event still downgrades to unverified either way). Getting it wrong would only produce a misleading reason string, not a false pass.
- **Files modified:** `tests/codex_review_run.py`, `tests/test_codex_review_container.py`
- **Verification:** Run 3's Step 4 output shows the corrected message (`"probe produced an unexpected event: error"`), and its investigation (stderr: `error=code-mode host is disabled`) confirmed the event was in fact a blocked-tool attempt, not a connectivity failure — the new label made that distinction legible for the owner's decision.
- **Committed in:** `28e0976` (fix)

- **Why:** the plan's authors apparently expected the live run to either cleanly pass or need a further code fix; a live run that is correctly behaving (disabled tool correctly blocked) but still trips the probe's fail-closed scoring was not an anticipated outcome shape
- **Cost if wrong:** if this judgment is mistaken — i.e. if the blocked-tool-attempt interpretation is wrong and something real was exposed — the residual risk is bounded by the same isolation properties already enforced (no host mounts, non-root, read-only root, dropped capabilities, confirmed container removal) and by the backlog item tracking a stricter probe-scoring rule for future runs; the post-merge live run on PR #47 is a second, independent live checkpoint that would surface the same signal again before the phase is ever called complete
