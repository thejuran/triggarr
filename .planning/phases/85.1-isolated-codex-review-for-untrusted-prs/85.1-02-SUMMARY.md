# Phase 85.1 Plan 02: Acceptance-Gate Wiring For Inspection-Only Codex Evidence Summary

**The owner-acceptance gate now accepts a COMPLETE inspection-only Codex result for a bot or fork head directly (no fallback needed), keeps the D-16 fallback available for a legitimate INCOMPLETE result, and blocks any anomalous "complete" claim outright through one completeness predicate shared by both `.github/scripts/codex-fallback.cjs` and `.github/scripts/acceptance-readiness.cjs`, proven by a dedicated 8-row parity test.**

## Accomplishments

- `INSPECTION_REVIEW_MODE` constant and the exported `inspectionOnlyCompleteness({meta, status, baseStatus, boundary, head, baseRequired})` predicate added to `codex-fallback.cjs`: returns `{complete, invalidEvidence, reasons}`, requiring a bound `complete` status, a `boundary.json` with `verdict: "verified"` bound to this head and attempt, and (when an audited input changed) a bound, complete base-status.
- `validateFallback`'s trust/Codex-status branch rewritten: a `complete: true` record is never rescued by a fallback for either trust level (one unified message); `invalidEvidence: true` is refused at every attempt, checked before any attempt-number rule; an untrusted head's legitimate `INCOMPLETE` inspection-only result needs attempt 2+ (mirroring the trusted-head retry rule) or a historical `untrusted-refused` record; a trusted head never accepts an inspection-only record as a fallback opener.
- `codexStatusFromOutput()` extended: for `review_mode: "inspection-only-ci-evidence"` it reads `<OUT>.boundary.json` (missing file never throws) and delegates to `inspectionOnlyCompleteness()`; the returned object gains `invalidEvidence` and `boundaryVerdict` (both `false`/`undefined` for trusted and `untrusted-refused` records, never silently wrong).
- `acceptance-readiness.cjs`'s `codexStatusFor()` now accepts a `boundary` input, blocks a trusted-mode "complete" claim for an untrusted head outright, and for an untrusted inspection-only record calls the same shared predicate: complete -> `ok` with detail `"complete (inspection-only, isolation boundary verified)"`; an anomalous complete claim -> blocked immediately with the predicate's reasons, fallback never consulted; a legitimate incomplete result falls through to the existing fallback path with updated wording (`INCOMPLETE/PENDING: no recorded fallback for this untrusted head; an owner-approved fallback (D-16) is required, or rerun the inspection-only review; wait or retry later blocks acceptance`, and `ok (owner-approved fallback for untrusted head: <name>)` on success).
- `runCli` in `acceptance-readiness.cjs` now reads `${opts.codexOut}.boundary.json` via the existing `readJsonIfPresent` helper and passes it through as `codex.boundary`.
- New `.github/scripts/codex-completeness-parity.test.cjs`: an 8-row fixture table (complete inspection-only; missing boundary with a complete claim; wrong-attempt boundary with a complete claim; audited change missing base-status; audited change with a complete bound base-status; trusted complete; legitimate INCOMPLETE at attempt 2; unverified-boundary complete claim at attempt 2) drives both `codexStatusFor` (no fallback) and `codexStatusFromOutput` for completeness parity, and both `readiness(+fallback)` and `validateFallback` directly for fallback-eligibility parity on every row where completeness is false.

## Assumption Drift (advisory)

- **Found during:** Task 1, writing the `test_invalid_evidence_never_opens_fallback` and "same with attempt 1" RED tests.
- **Planned:** The plan's prose reads as if a single "boundary missing, status complete, attempt 1" fixture should produce the generic `"needs its INCOMPLETE inspection-only ..."` reason (distinct from the attempt-2/3 invalid-evidence reason).
- **Actual:** Because `invalidEvidence` is computed independently of `attempt` (a missing/invalid boundary makes a "complete" claim invalid evidence at any attempt, by design — PC-06 requires this), that literal fixture would produce the *invalid-evidence* reason at attempt 1 too, not the generic one. I built two separate end-to-end fixtures instead: (a) status-complete + boundary-missing at attempt 2 -> invalid-evidence reason; (b) a genuinely *incomplete* status at attempt 1 -> the generic "needs attempt 2 or later" reason. Both are explicitly required elsewhere in the same behavior list, so this reads as the intended coverage rather than a gap.
- **Why:** PC-06's invariant ("no attempt number can turn invalid evidence into a fallback opener") is an explicit must-have; an attempt-dependent invalid-evidence reason would violate it.
- **Cost if wrong:** Low. If the two fixtures were meant to be the same case, the only consequence is one test asserts a message that's accurate but not what that specific plan sentence described; both the must-have invariant and all literal acceptance criteria are still met and verified.
