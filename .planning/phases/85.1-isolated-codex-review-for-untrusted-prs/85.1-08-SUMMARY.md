# Phase 85.1 Plan 08: Isolation Seam Fill-In -- Credential Custody, Container Lifecycle and the Verified Launch Summary

**verify_isolation_boundary() and run_untrusted_codex() now do real work: a one-read sign-in snapshot that passes a 7-day freshness preflight (D-11) is copied into the per-run `/codex-home`, a canary container proves the configuration before the review container is ever created, and `docker start -a -i` only runs on the container that was just inspected -- with every container and per-run directory owned by one ContainerLedger whose cleanup escalation survives an interrupt or a launch-preparation failure (B04-R3, B15, D-06, D-08, D-11).**

## Accomplishments

- `host_credential_path()`, `credential_preflight()` (7-day inclusive window per the D-11 amendment, future-timestamp guard, no token value ever in a message), `prepare_codex_home()` (reads the host file once, preflights it, then and only then writes a fresh 0700/`auth.json` 0600 copy and confirms the copy's hash matches before returning it), `credential_outcome()` (post-run hash compare against the exact snapshot copied; a changed, missing, symlinked or non-regular copy both make the run INCOMPLETE, with different messages for "refreshed" vs. "can't confirm"), `safe_read_regular_file()` (O_DIRECTORY|O_NOFOLLOW dir fd, O_NOFOLLOW|O_NONBLOCK file open, `fstat` `S_ISREG` check, size bound -- verified against a real symlink and a real FIFO) and `docker_env()` (PATH/HOME/DOCKER_HOST/DOCKER_CONTEXT/DOCKER_CONFIG only)
- `remove_container_confirmed()`: `docker rm -f` followed by `docker ps -a -q --no-trunc --filter id=<id>`; absence is what's confirmed, never the `rm` exit code; any indeterminate outcome (non-zero `ps`, unexpected output, either command raising) is "could not be confirmed removed," never silently clean
- `ContainerLedger`: `register()`/`register_dir()`/`release()`/`close()` (idempotent, never raises, continues past one failure to remove the rest) and a context-manager `__exit__` that runs `close()` on every path, prints every problem to stderr prefixed `ESCALATION: `, calls a caller-supplied `on_cleanup_problems` finalizer inside its own try/except so a failing finalizer only warns, and always returns `False` so an in-flight exception keeps propagating
- `verify_isolation_boundary()`'s real body: static inner-argv checks (every `DISABLED_FEATURES` entry disabled, the mounted schema used) before any docker call; `docker image inspect` against the expected label/version; the per-run directories checked against the host home/`REPO_ROOT`/host Codex home before creation; the credential snapshot and copy; schema staging; the canary's create/start/confirmed-removal/parse sequence (removed and confirmed before its stdout is ever parsed); the review container's create/inspect against `verify_container_config()`; returns `verified` with the public evidence (`container_id`, `image_id`, `mounts` with no host sources, `canary` markers, `credential.age_days`, ...) plus launcher-only keys (`_codex_home_dir`/`_out_dir`/`_schema_dir`/`_credential_sha256`) that `_execute_inspection()` never writes to `.boundary.json`
- `launch_in_verified_container()` + `run_untrusted_codex()` (thin wrapper): `docker start -a -i <the inspected id>` via the new shared `_stream_events()` helper (refactored out of the trusted path's `_run_codex`, same timeout/OSError contract, no behavior change for trusted runs); in a `finally`, confirmed removal always runs regardless of a clean exit, a non-zero exit, an `OSError` at start, a timeout, or a propagating interrupt; only on confirmed removal does it read `/out/last.json` (refusing a symlink or FIFO without hanging), write `<OUT>.last.json` by write-then-rename, run `credential_outcome()`, and delete the per-run directories
- `_record_cleanup_escalation()`: persists ledger cleanup problems into `<OUT>.status.json` from inside the ledger's `__exit__`, before any in-flight exception continues -- writes a fresh incomplete stub (naming the interrupt/failure cause) if no status exists yet, or merges the problems into an already-written status otherwise; never reads anything the container wrote
- `_execute_inspection()` now owns one `ContainerLedger` across boundary verification, launch preparation and the launch itself, folds any surviving `ledger.cleanup_problems` into INCOMPLETE on a normal exit, and writes `.boundary.json` with only the public (non-underscore-prefixed) keys

**1. [Rule 1 - Bug] `safe_read_regular_file()` didn't handle a symlinked directory cleanly**
- **Found during:** Task 1 GREEN verification
- **Issue:** Opening a symlinked directory with `O_DIRECTORY|O_NOFOLLOW` raises `NotADirectoryError` (not caught), crashing instead of refusing with `UnsafeOutputError`.
- **Fix:** Wrapped the directory open in its own try/except, wrapping any `OSError` other than `FileNotFoundError` as `UnsafeOutputError`.
- **Cost if wrong:** Low -- the failure mode was a crash (clearly visible), not a silent pass; a test (`test_safe_read_refuses_symlinked_directory`) now pins the correct refusal.
- **Files modified:** `tests/codex_review_run.py`

## Issues Encountered

One design resolution worth recording: the plan's Task 3 behavior list names a `test_cleanup_escalation_launch_prep_failure_execute_inspection` scenario where a RunnerError from "the launch-preparation step" is expected to propagate out of `_execute_inspection()` unchanged. The already-existing (Plan 85.1-06) orchestration test `test_untrusted_codex_launch_failure_is_incomplete` requires the opposite for `run_untrusted_codex()`'s own RunnerError -- it must stay caught locally and converted to a normal `INCOMPLETE`/exit-3 return, not propagate. Both are satisfied by injecting the two scenarios at different points: `run_untrusted_codex()`'s RunnerError stays caught (unchanged seam contract); the "launch-preparation failure" test instead monkeypatches the raw-output finalization step (`_finalize_raw_outputs`, which already runs in a `finally` around the launch) to write its own status stub and then raise, which is not caught by the narrower `except RunnerError` around `run_untrusted_codex()` alone and so genuinely propagates through the ledger's cleanup and back out, letting `_record_cleanup_escalation()` merge the manual-removal warning into the already-written status. No production code ambiguity remained once this was resolved; it only affected how the test was constructed.
