# Phase 85.1 Plan 07: Review Container Configuration and Deterministic Verification Summary

**The review container's exact `docker create` argv (and the canary check's matching argv, sharing one option builder), the host-exposure rule that keeps protected host paths out of both, a read-only hash-verified output-schema mount, and the two deterministic checks -- a static `docker inspect` comparison and an in-container canary-report parser -- that prove the running configuration matches, with B16's static/runtime environment sets kept separate and narrow.**

## Accomplishments

- `container_create_argv()`/`container_check_argv()` build the exact `docker create` argv for the review container and the in-container canary check from a single shared `_container_options()` helper (read-only rootfs, pinned tmpfs, non-root `10001:10001` user, dropped capabilities, `no-new-privileges`, a 256 pid limit, a 2g memory limit, `bridge` networking with no published ports, and exactly three per-run bind mounts); neither argv ever uses `docker run` or `--rm`, `-v`/`--volume`, `--privileged`, a host namespace flag, `--device`, `-p`/`--publish`, `--env-file`, the Docker socket, the host home, `REPO_ROOT`, the host `~/.codex`, or `SSH_AUTH_SOCK`.
- `host_exposure_problems()` enforces the one host-exposure rule (PC-03) for both argvs: no `--mount` source or `-e`/`--env-file` value may name a protected host path, and -- outside the canary argv's own inert positional path list -- no argv element anywhere may either; every reason names a path by marker only (`<HOST_HOME>`, `<REPO_ROOT>`, `<HOST_CODEX_HOME>`), never raw.
- `canary_paths()` builds the (path, marker) pairs the canary checks for absence (host home, repo root, host `~/.codex`, the SSH agent socket when set, a fresh host canary file, plus six fixed in-container paths); `CANARY_CHECK_SCRIPT` is a fixed POSIX `sh` script reporting presence/absence per path, `/work` entry count, `/codex-home` contents, the mounted schema's sha256, and environment variable *names only* (never values), terminated by `canary-done` -- verified syntactically valid (`sh -n`) and smoke-tested against the real system shell (no Docker) before being pinned into the golden argv tests.
- `stage_output_schema()` copies the audited schema into a per-run directory only after a sha256 match, using `O_CREAT|O_EXCL` and `fchmod(0o444)` so the copy is read-only regardless of umask; a hash mismatch or an existing destination both raise `RunnerError`.
- `verify_container_config()` statically compares a created container's `docker inspect` output against an `ExpectedContainer`, collecting a specific reason for every one of the threat model's named failure modes (extra/missing/mismatched mount, writable schema mount, extra tmpfs, wrong user, privileged, capabilities not dropped, writable rootfs, missing `no-new-privileges`, disabled security profile, non-bridge network, published ports, a host PID/IPC/UTS/user namespace, host devices, an unexpected environment name, an image/entrypoint/cmd mismatch, or unparseable/incomplete JSON) -- never raising, always collecting.
- `parse_canary_check()` parses the canary script's own report against an `ExpectedCanary`, flagging a visible canary path (by marker), a non-empty `/work`, unexpected `/codex-home` contents, a schema-hash mismatch, or an environment name outside `CONTAINER_BASE_ENV | CANARY_RUNTIME_ENV`; a missing `canary-done`, a missing expected path line, a duplicate line, or an unrecognized line all fail closed as `"could not parse canary check output"`.
- `CONTAINER_BASE_ENV = frozenset({"PATH", "HOME", "LANG", "CODEX_HOME"})` (the static check's only accepted names) and `CANARY_RUNTIME_ENV = frozenset({"HOSTNAME", "PWD"})` (the live canary's documented runtime addition) are disjoint, narrow sets -- `HOSTNAME`/`PWD` are rejected by `verify_container_config()` but accepted by `parse_canary_check()`, and `SHLVL` is rejected by both, confirmed by dedicated tests.
- `REVIEW_CODEX_VERSION = "0.153.4"` matches `docker/codex-review/Dockerfile`'s `ARG CODEX_VERSION`, pinned by a new `test_review_image_version_parity` in `tests/test_codex_review_image.py`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `host_exposure_problems()`'s protected-path matching picked the wrong marker for nested protected paths**
- **Found during:** Task 1 GREEN verification, running the new test suite for the first time
- **Issue:** The initial implementation returned the first protected-path prefix match in declaration order (`host_home`, then `repo_root`, then `host_codex_home`). Since a host's `~/.codex` is itself nested under the host home, a mount source set to `host_codex_home` matched `host_home`'s prefix check first and was reported as `<HOST_HOME>` instead of the more precise `<HOST_CODEX_HOME>`.
- **Fix:** Changed `_protected_marker()` to collect every matching protected prefix and return the marker for the longest (most specific) one, so a mount of the narrower path is always reported by its own marker.
- **Cost if wrong:** Low -- the mount would still be correctly rejected as a protected-host-path exposure either way (fail-closed is preserved); only the specific marker in the human-facing reason would be less precise (naming the broader `<HOST_HOME>` instead of `<HOST_CODEX_HOME>`), which matters for operator triage but not for the security guarantee itself.
- **Files modified:** `tests/codex_review_run.py`
- **Verification:** `uv run pytest tests/test_codex_review_container.py -q` -- all passing after the fix (was 2 failing before).
- **Committed in:** `60df090` (Task 1 GREEN commit; found and fixed before that commit, so no separate fix commit was needed)

**2. [Rule 1 - Bug] Test fixture nested one protected path under another, making a mutation test's own expectation ambiguous**
- **Found during:** Same test run as above
- **Issue:** The test file's `_REPO_ROOT_FAKE` fixture constant was originally defined as a subdirectory of `_HOST_HOME` (`/Users/example-owner/code/triggarr`), so a "mount source under repo_root" mutation test was *also* a "mount source under host_home" case, making the test's exact-marker assertion depend on matching-order coincidence rather than the property being tested.
- **Fix:** Changed `_REPO_ROOT_FAKE` to an unrelated path (`/opt/build/triggarr-checkout`), isolating each fixture to exercise exactly one protected-path marker at a time.
- **Cost if wrong:** Low -- test-fixture-only change; no effect on production behavior. Had this not been fixed, the test would have been fragile against the marker-priority fix above (Deviation 1), not a false negative in production.
- **Files modified:** `tests/test_codex_review_container.py`
- **Verification:** `uv run pytest tests/test_codex_review_container.py -q` -- all passing.
- **Committed in:** `60df090` (fixed before the first green run; the test file's committed RED state in `3b9ef84` already predates this fix, so the corrected fixture value lives in the GREEN commit's test-file diff)
