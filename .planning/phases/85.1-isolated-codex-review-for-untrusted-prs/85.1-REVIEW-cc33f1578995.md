## Summary

Reviewed the phase diff `a6ae60a..HEAD`, concentrating on `tests/codex_review_run.py` (the untrusted-PR inspection-only runner: PR/CI preconditions, inert input builder, trusted-main grader provenance, isolation boundary, credential custody, container lifecycle, completion gate), the inspection-only grading mode in `tests/codex_report_status.py`, the shared completeness predicate in `codex-fallback.cjs` / `acceptance-readiness.cjs`, and the review Dockerfile. No docker or codex command was run, and no credential file was read.

The container lifecycle is solid. The ledger confirms removal on every path, and output and credential copies are read only after that removal, using reads that never follow a symlink. The main problems are fail-open or weak checks around the container:

- **Completion gate fails open.** `completion_gate()` reports **pass** when `.status.json`, `.boundary.json` and `.grader-provenance.json` contain non-object JSON (for example `[]` or `null`). This was reproduced locally (CR-01).
- **Recorded outcome breaks the contract.** Some failures after the output name is reserved leave the attempt with no `.status.json` and exit 2 instead of INCOMPLETE/3 (WR-01).
- **Grading can drift from what was verified.** The untrusted path never re-checks its grader inputs after the 30-minute Codex run (WR-02). The "CI ready" evidence can be supplied by a job the untrusted head defines itself (WR-03).
- **Two completeness rules disagree.** The JS readiness check never looks at grader provenance, unlike the Python gate (WR-05).
- **Public evidence leaks local paths.** Absolute host paths, including the home directory, can reach evidence that is committed publicly without redaction (WR-06).
- **Known item, host-exposure check.** The narrowed `host_exposure_problems()` is graded WARNING (WR-04). It is defense in depth today: the review container's real configuration is re-checked through `docker inspect`. But it now misses `--opt=value`, `-v $HOME:/x`, `--volume` and `--env` forms. The canary container's configuration is never checked through `docker inspect`, so this argv check is the only static guard on it.

Convention checks (`gsd-tools verify conventions --check`) on the changed JS files returned no findings. No rule pack applies to Python.

## Critical Issues

### CR-01: completion_gate() passes when status, boundary or provenance records are not JSON objects

**File:** `tests/codex_review_run.py:3074-3118`
**Issue:** `_read()` returns `None` for any JSON value that parses but is not an object, and adds **no** reason. Every caller then guards its checks with `if x is not None:`, so a `.status.json`, `.boundary.json` or `.grader-provenance.json` containing `[]`, `null`, `"x"` or `1` skips its checks entirely. Only a *missing* provenance file adds a reason. Reproduced locally: a valid inspection-only `.meta.json` plus `[]` in each of the other three files makes `completion_gate()` return `[]`, which means **pass**, and `--completion-gate` exits 0.

This gate's documented job is fail-closed B18 completeness, and the checkpoint record names it as one of the two required acceptors. The JS readiness check happens to reject these files today, but the Python gate on its own reports COMPLETE for an attempt with no verified boundary, no complete status and no provenance. The same happens for an empty `.base-status.json` when one is required.

**Fix:**
```python
        try:
            parsed = json.loads(raw.decode("utf-8"))
        except (ValueError, UnicodeDecodeError):
            reasons.append(missing_reason or f"{prefix_text}{suffix} is not valid JSON")
            return None
        if not isinstance(parsed, dict):
            reasons.append(missing_reason or f"{prefix_text}{suffix} is not a JSON object")
            return None
        return parsed
```
Add gate tests for `[]` and `null` in each of the four records.

## Warnings

### WR-01: Some failures after the reservation leave the attempt with no .status.json and exit 2

**File:** `tests/codex_review_run.py:3691`, `3749-3751`, `3837-3839`
**Issue:** `_execute_untrusted()` re-raises `RunnerError` unchanged because "every RunnerError raised after the reservation has already written its status". Two paths break that rule:
- `materialize_grader()` (line 3691), when `git show` fails or the target file already exists.
- `audit_event_types()` (line 1250), which raises on any unparseable line.

The second path is realistic. On a timeout the docker client's process group is SIGKILLed, so the last `.jsonl` line can be cut off mid-write. `audit_event_types` then raises, and the run exits 2 with "error: could not audit Codex event stream". The reserved prefix is left with prompt, meta, boundary and provenance files but no status. That contradicts the contract that an untrusted run returns 0 or 3 and always records a status.

**Fix:** In `_execute_inspection`, wrap both calls and route failures through `_inspection_incomplete`:
```python
try:
    audit_reasons = audit_event_types(run.output(".jsonl"))
except RunnerError as exc:
    return _inspection_incomplete(run, str(exc))
```
Do the same around `materialize_grader`. Alternatively, in `_execute_untrusted`'s `except RunnerError`, write a stub when `.status.json` does not exist, as the `Exception` branch already does.

### WR-02: The untrusted path never re-checks the grader after the Codex run

**File:** `tests/codex_review_run.py:3755-3773` (compare with the trusted path at `3399-3407`)
**Issue:** `establish_trusted_main()` checks once, before the container starts, that HEAD equals the freshly fetched origin/main and that the audited inputs are clean. The checker at `REPO_ROOT/tests/codex_report_status.py` is then executed up to 30 minutes later with no re-audit. The trusted path re-runs `audit_inputs()` and compares hashes before grading.

If the operator switches branches or edits the checkout during the run, an untrusted head is graded by a checker that is not main's. Meanwhile `.grader-provenance.json` still reports `trusted-origin-main`, which breaks B13/D-02.

**Fix:** Before running the checker, re-run `audit_inputs()`, compare it with `inputs`, and re-check that `git rev-parse HEAD` equals `provenance["main_sha"]`. On a mismatch, return `_inspection_incomplete(...)`. A simpler alternative is to always grade with the checker materialized from `main_sha` through `materialize_grader`, never the working-tree file.

### WR-03: "CI ready" evidence for an untrusted head can come from a job the head defines

**File:** `tests/codex_review_run.py:762-796`
**Issue:** `ci_evidence()` accepts the highest-id check run named exactly "CI ready" for the head, from any app and any workflow. `pull_request` workflows run the PR's own workflow files, so a fork or bot head can add a workflow with a trivially passing job named `CI ready`. If that run gets the higher id, it overrides the real (possibly failing) CI ready, because "latest wins" does not mean "real CI". The result is recorded in `.ci-evidence.json`, and the prompt tells Codex that CI passed for exactly this head. That is the evidence the review is supposed to anchor on.

**Fix:** Require **every** "CI ready" run for the head to be `completed`/`success`, not just the latest. Also filter on `app.slug == "github-actions"`, and ideally on the check suite's workflow path (`.github/workflows/ci.yml`), by adding `app` to `_CHECK_RUN_FIELDS` and checking it. Report more than one "CI ready" run as suspicious.

### WR-04: The narrowed host_exposure_problems() misses several argv forms (known item, judged)

**File:** `tests/codex_review_run.py:1956-2059`
**Issue:** Only bare absolute-path tokens are resolved now. The following forms are no longer caught (or never were):
- `--mount=type=bind,src=$HOME,...` and `--volume=...`: the `--mount` branch matches only the separate-token form, and `--opt=...` is not absolute.
- `-v /Users/<u>:/h`: `realpath("/Users/u:/h")` is neither equal to `/Users/u` nor under `/Users/u/`.
- `--env X=Y`, `--env=X=Y` and `-eX=Y`: only `-e` is inspected. `--env-file=...` is not caught either.
- `_mount_src` reads only `src=`, so `source=` (also accepted by docker) and source-less mounts pass silently.
- `--privileged`, `--network=host`, `--pid=host`, `--cap-add` and `--device` are never checked in the argv, despite the docstring of `_container_options`.

Severity is WARNING, not BLOCKER: the runner builds both argvs from constants, and the review container is independently re-checked by `verify_container_config()` through `docker inspect`. However, the canary container is **never** inspected, so this argv check is its only static guard. A future edit to `_container_options` with `--opt=value` syntax would pass here unnoticed.

**Fix:** Replace the denylist with a structural allowlist. Assert that the option section of each argv equals `_container_options(codex_home_dir, out_dir, schema_dir)` exactly (plus `--entrypoint /bin/sh` for the canary), and reject everything else. If a scanner is kept, split `--opt=value` on the first `=`, check every `:`/`,`-separated absolute component, and accept `source=` as well as `src=`.

### WR-05: The JS readiness check ignores grader provenance and the output-prefix attempt, unlike the Python gate

**File:** `.github/scripts/codex-fallback.cjs:261-296`, `.github/scripts/acceptance-readiness.cjs:436-438`
**Issue:** `inspectionOnlyCompleteness()` checks status, boundary and base-status, but never reads `.grader-provenance.json`. `completion_gate()` requires `established`, `base_on_main is True` and `grader_source == "trusted-origin-main"`. Readiness also never checks that `meta.attempt` matches the `-aN` suffix of `--codex-out`, or that `meta.trusted === false`. The Python gate checks the attempt suffix.

So the two acceptors named in `docs/review-checkpoint-record.md` apply different rules, and the parity test only compares the two JS entry points with each other. D-02/B13 (the grader comes from trusted main) is therefore not enforced at acceptance.

**Fix:** Read `${codexOut}.grader-provenance.json` in `runCli` and `codexStatusFromOutput`, and require the same three fields inside `inspectionOnlyCompleteness`. Also require `meta.attempt` to equal the prefix's attempt number. Then add a cross-language parity fixture that runs the same records through `completion_gate()`.

### WR-06: Unredacted host paths, including the home directory, reach committed evidence

**File:** `tests/codex_review_run.py:2398`, `2487`, `2494`, `2116`, `2656`, `3716-3723`
**Issue:** Boundary reasons are written verbatim to `.boundary.json` and into the `.status.json` stub through `_inspection_incomplete`. Ledger problems reach `.status.json` the same way. Several of these messages embed absolute paths:
- `Codex sign-in file not found: /Users/<user>/.codex/auth.json`
- `refused: /Users/<user>/.codex could not be opened safely: OSError` (for example when `~/.codex` is a symlink and opening it with `O_NOFOLLOW` fails)
- `Codex sign-in copy destination already exists: <scratch>/codex-home`
- `output schema already staged: ...`
- `per-run directory could not be removed: ...: <path>`

These files are committed to the public repo. `redact_local_paths()` exists precisely because of that, but it is applied only to `.jsonl`/`.last.json`.

**Fix:** Pass every reason through `redact_local_paths()` before writing `.boundary.json` or any status stub, or name paths only by marker (`<HOST_CODEX_HOME>/auth.json`, `<SCRATCH>`) at the raise sites, as `host_exposure_problems` already does.

### WR-07: The open-PR check fails open on an unknown state

**File:** `tests/codex_review_run.py:835-836`
**Issue:** `if data.get("state") in ("CLOSED", "MERGED")` lets a missing, null or unexpected `state` through. D-09 says only an **open** PR is reviewed. The state is also never rechecked after the run, while `headRefOid` is (`_refetch_head_ref_oid`).

**Fix:** Use `if data.get("state") != "OPEN": raise RunnerError(...)`. Optionally request `state` in the post-run `gh pr view` and refuse a PR that closed during the run.

### WR-08: File names from the untrusted head are passed to git ls-tree as pathspecs

**File:** `tests/codex_review_run.py:883-889`, `958-959`
**Issue:** `_ls_tree_entry` passes each changed path, a name chosen by the untrusted head, as a pathspec. Verified locally: a file named `:(glob)b` makes `git ls-tree` die with "pathspec magic not supported". That raises `RunnerError` before the reservation, so the PR can never get an inspection-only review (denial of service, forcing the fallback). `:(top)x` and `:/x` are *accepted* magic: they look up a **different** path, so the file can be mislabelled "deleted at head" and its head content left out of the inert input.

**Fix:** Run every `GIT_SAFE_PREFIX` command with `--literal-pathspecs` (`git --literal-pathspecs -c ... ls-tree ...`), or set `GIT_LITERAL_PATHSPECS=1` in the env for those calls. Better still, take the modes from a single `git ls-tree -r -z <head>` and look paths up in a dict.

### WR-09: The review image is trusted by tag and label only, though the docstring claims a recorded-id check

**File:** `tests/codex_review_run.py:1289-1315`, `1333-1335`
**Issue:** The `verify_isolation_boundary` docstring says the image is checked "against the expected label and recorded image id". In fact, any local image tagged `triggarr-codex-review:0.153.4` that carries label `org.triggarr.codex-review=0.153.4` is accepted, and `image_id` is only captured and compared with the container's own `Image`. A label is trivially set by any `docker build`, for example one run from a checkout of an untrusted branch that edits `docker/codex-review/Dockerfile`. The canary cannot detect a modified `codex` binary that ignores `--disable`, so the static boundary rests on an unpinned image.

**Fix:** Record the expected image id (or the Dockerfile's sha256 plus a build-from-main step) in a committed/audited place and compare it. At minimum, add a `org.triggarr.codex-review.dockerfile-sha256` label at build time and compare it with the sha256 of the committed Dockerfile on main. Correct the docstring either way.

### WR-10: The digest-pinned review image has no Dependabot coverage

**File:** `.github/dependabot.yml:25-34`, `docker/codex-review/Dockerfile:388,405`
**Issue:** The `docker` ecosystem covers `directory: "/"` only. The new `docker/codex-review/Dockerfile` pins `debian:bookworm-slim@sha256:...`, and nothing will ever propose updates for it, so the image that holds the owner's Codex sign-in will silently accumulate base-image CVEs. The user's release rule depends on Dependabot surfacing these.

**Fix:** Add a second `docker` entry with `directory: "/docker/codex-review"` and the same cooldown and grouping. Note that a digest bump also changes the review image, which is classified as sensitive.

## Info

### IN-01: The Dockerfile installs an arm64-only binary without pinning the platform

**File:** `docker/codex-review/Dockerfile:388-402`
**Issue:** Only `codex-aarch64-unknown-linux-musl` is fetched, but `FROM` has no `--platform=linux/arm64`. On an amd64 host the build succeeds and the canary passes, because it runs `/bin/sh`, but Codex fails with "exec format error" at launch. This fails closed, but only after the credential copy has been staged.
**Fix:** Add `FROM --platform=linux/arm64 ...` to both stages, or select the binary by `TARGETARCH` with per-arch checksums.

### IN-02: The untrusted path's cross-grade is redundant, and its "predates --review-mode" branch is effectively unreachable

**File:** `tests/codex_review_run.py:3689-3698`, `3776-3784`
**Issue:** `establish_trusted_main` already requires harness HEAD == `main_sha`, so the REPO_ROOT checker and the "trusted-main" checker are the same bytes. The cross-grade runs one checker twice. The `--help` probe could only fail if the running checker itself were broken, and in that case the head-side grading fails too.
**Fix:** Document this as an intentional belt-and-braces check, or (preferably, see WR-02) grade only with the materialized `main_sha` checker.

### IN-03: The protected-path marker logic is duplicated, and a docstring is wrong

**File:** `tests/codex_review_run.py:1265-1286` vs `1985-2005`
**Issue:** The `_protected_path_marker` docstring says it is "Shared by host_exposure_problems()", but `host_exposure_problems` defines its own identical `_protected_marker` closure. The two can drift.
**Fix:** Make `host_exposure_problems` call `_protected_path_marker`.

### IN-04: The inspection-input stats classify a file by its content prefix

**File:** `tests/codex_review_run.py:964-968`
**Issue:** A text file whose real content starts with "content omitted", "symlink" or "submodule" is counted as omitted. The same applies to file-section headers: file content containing `#### other/path` can imitate another file's section inside the fenced input.
**Fix:** Have `_inspected_file_note` return `(text, included: bool)`, and consider showing each file's content in its own fenced sub-block.

### IN-05: The completion-gate prefix regex accepts `..` as the phase-directory segment

**File:** `tests/codex_review_run.py:176` (and `OUT_PATH_RE` in `acceptance-readiness.cjs:31`)
**Issue:** `[A-Za-z0-9._-]+` matches `..`, so `.planning/phases/../codex/<x>` is accepted as a prefix shape. It stays inside the repo and fails on missing files, but it is not the "exact shape" the docstring promises.
**Fix:** Require a leading alphanumeric character, for example `[A-Za-z0-9][A-Za-z0-9._-]*`, in both regexes, which a drift test already keeps in step.

### IN-06: The launch `finally` loses the credential-refresh warning on interrupt, and an OSError can mask the original exception

**File:** `tests/codex_review_run.py:1615-1636`
**Issue:**
- With an exception in flight, `problems`, including the "Codex refreshed its sign-in... re-login needed" message, is computed and then discarded.
- If `_write_bytes_atomic` raises `OSError` inside the `finally`, it replaces the in-flight exception and skips `credential_outcome` and the `rmtree`. The ledger still deletes the directory.
- The docstring says the per-run directories are "left registered" when removal is unconfirmed, but `ContainerLedger.close()` deletes them anyway.
**Fix:** Print `problems` to stderr when `in_flight` is set, guard `_write_bytes_atomic` with `try/except OSError` that appends a problem, and align the docstring with the ledger's behavior.

### IN-07: audit_event_types() only inspects item.completed

**File:** `tests/codex_review_run.py:1257-1261`
**Issue:** A tool item that appears in `item.started`/`item.updated` but never completes, for example when the stream is cut by the timeout, is not reported. Other gates make the run INCOMPLETE in that case (the timeout exit code), so the effect is low, but the audit's own claim is broader than its check.
**Fix:** Check `item.type` on `item.started` and `item.updated` events too.

### IN-08: The unused `run` parameter on launch_in_verified_container

**File:** `tests/codex_review_run.py:1577`
**Issue:** `run` is accepted "for the same call shape" and never used, and `run_untrusted_codex` uses `del inner_argv` to discard its own argument. Both are dead parameters on a security seam.
**Fix:** Remove them, or prefix them with `_`.

## Set aside (needs ruling)

### SA-01: The container cannot use its per-run bind mounts on a Linux Docker host

**Where:** `tests/codex_review_run.py:1393`, `2492`, `1837`
**Why excluded:** Portability is outside this review's correctness scope. The owner runs Docker Desktop on macOS, which remaps file ownership on bind mounts.
**Effect if left as is:** On native Linux Docker, `scratch` (0700, from `mkdtemp`), `codex-home` (0700) and `out` are owned by the host user, and container uid 10001 cannot read `auth.json` or write `/out/last.json`. The canary reports "unexpected /codex-home contents", so every untrusted review is INCOMPLETE. This fails closed but the feature does not work there.
**Needs:** A ruling on whether Linux hosts are in scope (if so, add a `chown`, or use `--userns`/ACLs), or record macOS-only as a constraint in the contract.
