## Info

### IN-01: An interrupted create can still leave a container if the daemon finishes creating it after cleanup has checked

**File:** `tests/codex_review_run.py:1787-1797`, `:1819-1829`, `:3047-3097` (`remove_container_confirmed`), `:3157-3166` (`ContainerLedger.close`)
**Issue:**
- **How create runs:** `docker create` goes through plain `subprocess.run` (`run_command`, `:338-339`). On Ctrl-C, the CLI child gets SIGINT too, `subprocess.run` waits about 0.25 s, then kills it, and the CLI aborts its HTTP request. The daemon may still be in the middle of the create.
- **The race:** `ContainerLedger.__exit__` then runs `docker rm -f <name>` and `docker ps --filter name=<name>` straight away. If the daemon commits the container after that `ps`, cleanup reports clean (`cleanup_problems == []`) and the container is left behind with no escalation. This is F001's outcome in a much narrower window: milliseconds instead of the whole response path.
- **Impact:** the leftover would be a stopped, never-started container whose bind-mount sources (the per-run dirs) the ledger has already deleted. It is the same "stopped-container lifecycle leak, not an escape" class that Codex graded for F001.
- **Evidence:** reasoned from `subprocess.run`'s interrupt handling and Docker's client/daemon split. Not reproduced, since no docker command was allowed. Whether Moby cancels an in-flight create when the client disconnects varies by version.
**Fix:** In `close()`, for a name with no bound ID only, confirm absence twice with a short gap (for example, `ps` → sleep 1 s → `rm -f` + `ps` again), and escalate if the second check finds it. Alternatively, accept and document the residual in the `ContainerLedger` docstring: "a create the daemon completes after cleanup's absence check is not detected". Either way, add one fake-runner test where the container appears only on the second `ps`.

### IN-02: The create-exited-non-zero branches have no test, including the most common case where no container exists

**File:** `tests/codex_review_run.py:1792-1793`, `:1824-1825`; `tests/test_codex_review_container.py` (no `create exited` test)
**Issue:**
- **What changed:** round 5 changed what these branches do on cleanup. Before, nothing was registered, so nothing was cleaned up. Now the name is registered with no ID, so `close()` runs `rm -f <name>` and `ps --filter name=<name>`.
- **What is untested:** `grep "create exited"` finds no test in either container or inspection suites. Two cases should be pinned:
  - the ordinary failure (image missing, daemon refuses), where no container exists and cleanup must report **no** escalation, so a clean failure is not turned into a false "could not be confirmed removed";
  - a failure exit where the daemon did create the container, which must be removed by name.
- **Why it matters:** the current `_DockerRunner` can model neither (create always adds to `live` and returns 0 or raises). A future change to the name-filter handling could make every failed create escalate, or silently stop removing a half-created one, without a test noticing.
**Fix:** Add a `create_exit_code: dict[str, tuple[int, bool]]` option to `_DockerRunner` (exit code, and whether the daemon-side container exists). Add a parametrised boundary test over canary/review x {created, not created}: assert `verdict == "unverified"` with "docker create exited", that the orphan is gone when created, and that `ledger.cleanup_problems == []` in both cases.
