# Requirements: Triggarr — v2.12 Search Correctness & Trustworthy Feedback

**Defined:** 2026-10-08
**Core Value:** Reliably trigger searches in Radarr, Sonarr, and Lidarr for missing and upgrade-eligible media on a schedule, with closed-loop feedback showing what was actually grabbed — without exposing credentials or expanding attack surface.
**Source of truth:** `docs/superpowers/specs/2026-10-08-search-correctness-design.md` (grading definitions §3.1–3.3; per-phase behavior + acceptance §4)

## v2.12 Requirements

### Log Hygiene (LOGSEC)

- [x] **LOGSEC-01**: The reset token never appears in the in-app log viewer or in any HTTP response; viewer-buffer entries stay redacted after the token is consumed, expires, or is replaced.
- [x] **LOGSEC-02**: The operator can still read the reset token from the stderr log (`docker logs`).
- [x] **LOGSEC-03**: Any *arr HTTP error whose request URL contains an API key is logged with the key redacted, including Sonarr `detect_api_version` on legacy installs.

### Cycle Outcomes (OUTCOME)

- [x] **OUTCOME-01**: Each instance records its last cycle as Success, Partial, Failed, or Nothing needed searching, per spec §3.1 (only queues with search count > 0 are active).
- [x] **OUTCOME-02**: "Last successful search" updates only when ≥1 command was accepted by the *arr; "Last checked" updates whenever a cycle finishes; connection health stays a separate signal.
- [x] **OUTCOME-03**: A pre-upgrade `last_success` timestamp displays as "Last success (legacy)" until the instance's first new cycle.
- [x] **OUTCOME-04**: The consecutive-failure counter increments on Failed and resets on Success, Partial, or Nothing needed searching.
- [x] **OUTCOME-05**: The dashboard card shows "<Grade> · N accepted, M failed · <relative time>", amber for Partial / red for Failed, with an expandable sanitized error detail.
- [x] **OUTCOME-06**: An accepted command whose history write fails is still counted as accepted, updates "last successful search", and shows a separate persistence warning — never counted as failed, never retried.

### Tag Scope (TAGSCOPE)

- [x] **TAGSCOPE-01**: When a queue's configured tag can't be resolved (tag fetch failed or tag no longer exists), that queue issues zero searches; the other queue runs if its own scope resolves.
- [x] **TAGSCOPE-02**: A persistent card warning names the skipped queue and reason, and clears automatically once the tag resolves.
- [x] **TAGSCOPE-03**: A skipped queue counts as unevaluated for grading; a blocked queue plus an empty queue grades Failed.
- [x] **TAGSCOPE-04**: README/docs no longer describe the search-everything fallback.

### Cycle Robustness (ROBUST)

- [x] **ROBUST-01**: A malformed *arr record (null nested series/artist, malformed or naive grab date, non-string version) is skipped and logged; the cycle completes and its state persists.
- [x] **ROBUST-02**: A failure in any history insert (failure path or success path) is logged and does not abort the batch.
- [x] **ROBUST-03**: Tag autocomplete returns its documented empty-`<datalist>` fallback instead of a 500 on `ValueError`/JSON errors.
- [x] **ROBUST-04**: Search-side malformed records are reported in the cycle detail and degrade the grade per §3.1, but are not counted as failed commands.

### Sonarr Season Dedup (DEDUP)

- [x] **DEDUP-01**: Within one Sonarr cycle, each (series, season) receives at most one engine dispatch across the missing and upgrade queues; the missing queue claims a season on attempt, even if its command fails.
- [x] **DEDUP-02**: The upgrade queue skips claimed seasons without consuming batch slots, and the skipped season keeps its existing upgrade searched-log position.
  - *Amendment DEDUP-03 (2026-10-18, PR #28 review; spec §4 Phase 80):* A season claimed by the missing queue counts as covered for the upgrade queue's pass (whatever the missing command's outcome) but is never inserted into upgrade history; an empty upgrade batch never completes a pass. (Added 2026-10-18 from the PR #28 review; amends v2.11 QUEUE-09 for claimed seasons.)

### Sonarr Grab Attribution (ATTR)

- [x] **ATTR-01**: A Sonarr grab credits a search only when both series and season match.
- [x] **ATTR-02**: Each grab is credited at most once, ever, keyed by (app, stable instance ID, grab ID) — across instances with colliding grab IDs, instance renames, restarts, and history pruning (no cascading deletion of ownership records).
- [x] **ATTR-03**: Each instance has a permanent Triggarr-assigned ID, generated at creation, backfilled for existing instances on first load, persisted via the atomic config write, and unchanged by renames.
- [x] **ATTR-04**: Search↔grab ownership is committed in the same transaction as outcome/stat updates; later checks include a search's previously owned grabs, and results count distinct episodes.
- [x] **ATTR-05**: Pre-cutover pending searches keep their rows and counters, are excluded from corrected attribution and from the active pending cap, and display as "Legacy — tracking discontinued".
- [x] **ATTR-06**: Sonarr effectiveness stats show "Attribution corrected on <date>. Earlier results may include misattributed or double-counted grabs."; totals including pre-cutover data are labelled "Lifetime — includes historical estimates"; the cutover is recorded exactly once after a successful migration. Note and labels show only where pre-fix Sonarr data exists (per instance, per metric; refined 2026-10-18, see 81-CONTEXT D-01..D-08).
  - Owner-reviewed on screen, Plan 81-09 Task 2 (two `/walkthrough` runs, 2026-10-20/21): CP1-CP6 pass both before and after two bounded scope additions (stats-card retitle, selector/poll `hx-sync` race fix). Owner response: "Accepted." See `81-LIVE-MATRIX.md` "Owner review (disclosure)".

### Sonarr v5 Compatibility (SONARRV5)

- [x] **SONARRV5-01**: Application-version reporting correctly identifies v5, preserves v3/v4 reporting, and handles malformed versions safely without selecting API routes from the application major version.
- [x] **SONARRV5-02**: An isolated v4/v5 smoke matrix verifies connection, tags, missing/cutoff pagination, library counts, season commands, and grab tracking; exact builds and sanitized results are recorded. Existing v3 routes and API-key authentication remain unless a demonstrated failure requires a targeted fix. Untested scenarios remain explicitly unverified.
  - **Closed 2026-10-21 by owner decision after Plan 81-14.** The remaining D-11 live criteria passed on the isolated sandboxes, zero searches. Client-returned episode-ID sets were observed in-process from the real `SonarrClient` (cycle and Refresh-counts call paths) and were complete and duplicate-free against independent Sonarr reads over 2+ pages, for missing and cutoff pagination on v5 (19/28 episodes) and v4 (19/8). A dedicated v4 Refresh-counts run matched Sonarr (connected; missing, cutoff and library totals). Earlier live passes are unchanged: connection/version, tags, controlled SeasonSearch, scheduled cycles, repeated tracking checks (probe-assisted), v5 and v4 season-pack credit, `/api/v3` routes and API-key auth. Builds: Sonarr 5.0.0.2701 and 4.0.20.3014; Triggarr `b35470b` (client/count code identical to `363060e`). See `81-LIVE-MATRIX.md` "Plan 81-14" and "## Status".
  - **Explicitly unverified-live (D-12 fallback, owner decision 2026-10-21):** multi-season pack (no cross-season leakage) and alternate series order. Both satisfy D-12 through representative sanitized fixtures and real-client-path regression tests (4 passed at `363060e`), not live evidence, and this waives no mandatory live criterion. Also not live-verified: unattended repeated tracking over scheduled cycles (probe-assisted only) and the Refresh-counts HTTP route on v4 (route shown in 81-13; function-level dedicated run in 81-14). Full v5 support is not claimed beyond these results.
- [x] **SONARRV5-03**: Attribution regression fixtures cover alternate series orders, season packs, and multi-season releases using Sonarr-returned identities, with distinct-episode counting and no cross-season or repeated credit.
