## Findings

### [HIGH] SHIELD-001: Missing Content-Security-Policy Header

- **File:** `triggarr/web/middleware.py:30`
- **CWE:** CWE-1021 (Improper Restriction of Rendered UI)
- **OWASP:** A05:2021 Security Misconfiguration
- **Tool:** manual-review

#### Description

`SecurityHeadersMiddleware` sets `X-Frame-Options`, `X-Content-Type-Options`, and `Referrer-Policy`, but omits a `Content-Security-Policy` header. The application loads inline scripts (htmx, changelog modal), renders user-controlled data (instance names, item names from Radarr/Sonarr search history) in HTML. Without CSP, any XSS vector has no browser-side mitigation.

#### Impact

If an XSS vector is introduced (e.g., stored item names containing HTML entities not caught by Jinja2 autoescape), an attacker can exfiltrate the API key (rendered in plaintext on settings page — see SHIELD-002), perform actions on behalf of the victim, or inject malicious scripts.

#### Proposed Fix

```diff
  response.headers["X-Frame-Options"] = "SAMEORIGIN"
  response.headers["X-Content-Type-Options"] = "nosniff"
  response.headers["Referrer-Policy"] = "same-origin"
+ response.headers["Content-Security-Policy"] = (
+     "default-src 'self'; "
+     "script-src 'self' 'unsafe-inline'; "
+     "style-src 'self'; "
+     "img-src 'self' data:; "
+     "connect-src 'self'; "
+     "frame-ancestors 'none'"
+ )
```

#### Compliance Impact

- **SOC 2:** CC6.1 (Logical access security), CC7.1 (System monitoring)
- **PCI-DSS:** 6.5.10 (Broken authentication and session management)

### [HIGH] SHIELD-002: API Key Rendered in Plaintext HTML Response

- **File:** `triggarr/web/routes.py:401`
- **CWE:** CWE-312 (Cleartext Storage of Sensitive Information)
- **OWASP:** A02:2021 Cryptographic Failures

#### Description

The settings page passes the raw API key to the template context via `settings.auth.api_key.get_secret_value()`. The template renders it into an `<input type="password">` (masked visually), but the **full key is in the HTML source**. Browser dev tools, extensions, page source view, and HTTP response caches all expose it.

#### Impact

The API key grants full unauthenticated programmatic access to Triggarr. Embedding it in page HTML means any XSS, browser extension, screen-sharing session, or cached HTML file exposes a persistent credential.

#### Proposed Fix

```diff
- "auth_api_key": settings.auth.api_key.get_secret_value(),
+ "auth_api_key_set": bool(settings.auth.api_key.get_secret_value()),
```

Redesign the template to show `****` as placeholder. Only reveal the key via a separate authenticated JSON endpoint, or only show it immediately after regeneration (the existing `revealed=True` path).

#### Compliance Impact

- **SOC 2:** CC6.1 (Logical access), CC6.7 (Encryption of sensitive data)
- **PCI-DSS:** 3.4 (Render PAN unreadable), 6.5.3 (Insecure cryptographic storage)

### [HIGH] SHIELD-003: No Brute-Force Protection on Login Endpoint

- **File:** `triggarr/web/routes.py:1126`
- **CWE:** CWE-307 (Improper Restriction of Excessive Authentication Attempts)
- **OWASP:** A07:2021 Identification and Authentication Failures

#### Description

The `POST /login` endpoint has no rate limiting, account lockout, or delay on failed attempts. An attacker can submit unlimited credential guesses. This is significant because Triggarr is deployed on home networks where port 8484 may be exposed, and there's a single admin account.

#### Impact

bcrypt with 12 rounds provides ~250ms per verification. An attacker limited only by network RTT can test 2-4 guesses/second. A short password can be brute-forced in hours.

#### Proposed Fix

```diff
+ _login_fail_times: dict[str, list[float]] = {}
+ _LOGIN_MAX_ATTEMPTS = 10
+ _LOGIN_WINDOW_SECONDS = 300

  @router.post("/login", response_model=None)
  async def login_post(request: Request) -> HTMLResponse | RedirectResponse:
+     remote_ip = request.client.host if request.client else "unknown"
+     if _is_login_rate_limited(remote_ip):
+         return HTMLResponse("Too many login attempts. Try again later.", status_code=429)
      ...
      # on failure:
+     _record_login_failure(remote_ip)
+     await asyncio.sleep(0.5)
```

#### Compliance Impact

- **SOC 2:** CC6.1, CC6.2 (Prior to issuing system credentials)
- **PCI-DSS:** 8.1 (Identification and authentication policies)

### [HIGH] SHIELD-004: Hardcoded Test API Keys in Git History

- **File:** `tests/test_auth_middleware.py:61` (+ 11 more occurrences)
- **CWE:** CWE-798 (Use of Hard-coded Credentials)
- **OWASP:** A02:2021 Cryptographic Failures
- **Tool:** gitleaks

#### Description

Gitleaks detected 12 occurrences of `generic-api-key` patterns across test files and `.planning/` documentation. Most are test fixture values (e.g., `_API_KEY = "abcdef12..."`), not real production secrets.

#### Impact

These appear to be **test-only fixture values**, not real credentials. The risk is LOW in practice but HIGH by gitleaks classification. The `.planning/` directory should be excluded from the repository if it contains example credentials. Test files should use clearly fake values (e.g., `"test-api-key-not-real"`).

#### Proposed Fix

Add `.gitleaksignore` or use clearly fake test constants:
```diff
- _API_KEY = "abcdef1234567890abcdef1234567890"
+ _API_KEY = "test-only-not-a-real-key-00000000"
```

#### Compliance Impact

- **SOC 2:** CC6.1, CC6.7
- **PCI-DSS:** 6.5.3

### [MEDIUM] SHIELD-005: Username Logged on Auth Failure (PII in Logs)

- **File:** `triggarr/web/routes.py:1158`
- **CWE:** CWE-532 (Insertion of Sensitive Information into Log File)
- **OWASP:** A09:2021 Security Logging and Monitoring Failures

#### Description

On failed login, the submitted username is written to logs. This is user-controlled input. If a user accidentally types their password into the username field, it appears in logs in cleartext. The redacting sink does not cover `auth.username`.

#### Proposed Fix

```diff
- logger.warning("Login failed for user {username}", username=username)
+ logger.warning("Login failed: username_match={matched}", matched=bool(username and username == auth.username))
```

#### Compliance Impact

- **SOC 2:** CC7.2, CC7.3 (System monitoring)
- **PCI-DSS:** 10.1 (Audit trails)

### [MEDIUM] SHIELD-006: CSRF Mitigation Bypassable Without Origin/Referer

- **File:** `triggarr/web/middleware.py:57`
- **CWE:** CWE-352 (Cross-Site Request Forgery)
- **OWASP:** A01:2021 Broken Access Control

#### Description

`OriginCheckMiddleware` allows requests where both `Origin` and `Referer` headers are absent. Non-browser HTTP clients omit both by default. SameSite=Lax cookies provide a strong secondary defense, but defense-in-depth recommends CSRF tokens for sensitive mutations.

#### Proposed Fix

Add synchronizer CSRF tokens to sensitive forms (password change, API key regeneration, settings save). The existing SameSite=Lax cookie is a good baseline.

#### Compliance Impact

- **SOC 2:** CC6.1, CC6.3
- **PCI-DSS:** 6.5.8, 7.1

### [MEDIUM] SHIELD-007: SSRF Partial Bypass via IPv4-Mapped IPv6

- **File:** `triggarr/web/validation.py:80`
- **CWE:** CWE-918 (Server-Side Request Forgery)
- **OWASP:** A10:2021 Server-Side Request Forgery

#### Description

`validate_arr_url` blocks loopback and link-local IPv4, but does not check IPv4-mapped IPv6 addresses like `::ffff:169.254.169.254` or multicast addresses. DNS rebinding is also not mitigated.

#### Proposed Fix

```diff
  try:
      addr = ipaddress.ip_address(hostname)
-     if addr.is_link_local or addr.is_loopback or addr.is_unspecified:
+     if addr.is_link_local or addr.is_loopback or addr.is_unspecified or addr.is_multicast:
          return (False, "Blocked address")
+     if isinstance(addr, ipaddress.IPv6Address) and addr.ipv4_mapped:
+         mapped = addr.ipv4_mapped
+         if mapped.is_link_local or mapped.is_loopback:
+             return (False, "Blocked address")
  except ValueError:
      pass
```

#### Compliance Impact

- **SOC 2:** CC6.1
- **PCI-DSS:** 6.5.9

### [MEDIUM] SHIELD-008: Sessions Not Invalidated on Password Change

- **File:** `triggarr/web/routes.py:1170`, `triggarr/auth.py:88`
- **CWE:** CWE-613 (Insufficient Session Expiration)
- **OWASP:** A07:2021 Identification and Authentication Failures

#### Description

Sessions are HMAC-signed tokens with 30-day max age and no server-side store. Logout only deletes the client cookie. Password change does not rotate `session_secret`, so existing signed cookies remain valid. A test (`test_password_change_old_session_still_valid`) explicitly asserts this behavior.

#### Proposed Fix

Rotate `session_secret` on password change to invalidate all sessions:
```diff
  new_auth = current_settings.auth.model_copy(update={"password_hash": SecretStr(new_hash)})
+ new_secret = generate_session_secret()
+ new_auth = new_auth.model_copy(update={"session_secret": SecretStr(new_secret)})
```

#### Compliance Impact

- **SOC 2:** CC6.1, CC6.2
- **PCI-DSS:** 8.1, 6.5.10
